# E3 — краткая инструкция прогона

Полное ТЗ с обоснованиями — `paper/E3_spec.md`. Здесь только то, что нужно
набрать. Если что-то из написанного ниже кажется странным, ответ на «почему»
есть в спеке, ссылки на разделы проставлены.

Модель берётся **по сети** через OpenRouter. Локальная видеокарта не нужна
нигде, кроме отрисовки RViz.

---

## 0. Что должно получиться

56 прогонов, около 7 часов работы, ~4.5 ГБ записей, **$4.5–7** по ключу. Один
прогон = одна папка `paper/results/sessions/<метка времени>/`, её отдают целиком.

---

## 1. Разовый сетап после клона

### 1.1 Ключ

Завести ключ на OpenRouter **с лимитом** (не бессрочный) и положить в `.env` в
корне репозитория. Файл уже в `.gitignore`.

```bash
git clone <repo> && cd llm_swarm
printf 'API_KEY=sk-or-v1-...\n' > .env
```

### 1.2 Что уже сделано в репозитории

Ничего доустанавливать и патчить не нужно — перечислено, чтобы было понятно,
откуда что берётся:

- OpenRouter принимается как точка входа (`orchestrator.launch.py`);
- compose подставляет `${API_KEY}` из `.env` в оба сервиса, поэтому `-e` в
  каждом `exec` не нужен; туда же уходят `OPENROUTER_PROVIDER`,
  `OPENROUTER_ALLOW_FALLBACKS`, `LLM_CALL_DELAY_SEC`;
- `record_session.sh` понимает `--llm-endpoint` и пишет в `session.json` блоки
  `llm_endpoint` и `llm_routing`, а при пустом ключе или неприбитом провайдере
  ругается в консоль;
- потолок контекста поднят до 65536, таймаут вызова до 120 с — без этого цикл
  инструментов обрывался исключением на четвёртой итерации (`E3_spec.md` §4.3).

- скриптованный водитель для ячейки no-LLM написан:
  `ros2 run iros_llm_swarm_bt e3_scripted_driver`;
- дефект расписания PBS исправлен (`time_step_sec` `0.1` → `0.4`), отдельной
  правки перед ячейкой PBS больше не нужно.

**Ничего дописывать не нужно** — сетка идёт целиком.

### 1.3 Контейнер и сборка

Прибить провайдера **до** подъёма контейнера — compose читает эти переменные
при создании контейнера, а не при каждом `exec`:

```bash
export OPENROUTER_PROVIDER=Chutes
export LLM_CALL_DELAY_SEC=1

docker compose up -d terminal          # terminal-cpu, если нет NVIDIA
docker compose exec terminal bash
```

Проверить, что ключ и маршрутизация доехали:

```bash
docker compose exec terminal bash -lc 'echo "$OPENROUTER_PROVIDER / ${LLM_API_KEY:0:12}…"'
```

Дальше всё **внутри** контейнера:

```bash
cd /home/fabian/ros2_ws
colcon build --packages-select iros_llm_swarm_interfaces iros_llm_swarm_mapf_lns
colcon build
```

Первая строка обязательно первой — остальные пакеты зависят от её типов.

**`build/` и `install/` живут внутри контейнера, а не в репозитории.**
Из репозитория смонтирован только `src`. Значит любое пересоздание
контейнера — правка `docker-compose.yaml`, `docker compose down`, смена сервиса
с `terminal` на `terminal-cpu` — **стирает всю сборку**, и следующий запуск
поднимется на пустом workspace. Это минут десять посреди смены. Правило: compose
трогать только между сменами и после любой правки пересобирать с нуля.

**Записи сессий уничтожались тем же способом, и это уже исправлено.**
`record_session.sh` писал в `$HOME/swarm_sessions`, а `$HOME` — это
`/home/fabian` **внутри** контейнера, то есть тот же перезаписываемый слой.
Кампания на 7.5 часов и несколько долларов API исчезала от одного
`docker compose down`.

Теперь записи ложатся в **`paper/results/sessions/<метка времени>/`**, то есть
внутрь уже смонтированного `src`. Отдельного монтажа не потребовалось, и это
важно: добавление тома в compose само пересоздало бы контейнер и снесло сборку.

**В git уходит только лёгкое.** Бэги остаются на машине исполнителя и
собираются файлами по запросу.

| в git | локально |
|---|---|
| `session.json` | `bag/*.db3` |
| `llm_chat/*.jsonl` | `launch.log` |
| `llm_decisions/`, `llm_commands/` | `bag_record.log` |
| `bag/metadata.yaml` | |

`metadata.yaml` оставлен намеренно: это индекс rosbag2 со списком топиков и
счётчиками сообщений, то есть ответ на «правильно ли записалось» без выкачивания
самого бэга. `launch.log` не коммитится — на 20 роботов с Nav2 это мегабайты на
прогон.

Коммитить свои сессии после смены:

```bash
git add paper/results/sessions/
git status --short | head       # .db3 в списке быть не должно
```

Путь переопределяется переменной `SWARM_SESSIONS_DIR`, если нужно писать на
другой диск:

```bash
SWARM_SESSIONS_DIR=/mnt/data/e3 bash .../easy_record.sh --B
```

**Не добавлять `--symlink-install` к `iros_llm_orchestrator`.** У пакета старый
setuptools, и сборка падает с `error: option --editable not recognized`. Хуже
того, неудачная попытка оставляет состояние, из-за которого **следующая обычная
сборка тоже падает**, уже с `--uninstall not recognized`. Лечится так:

```bash
rm -rf build/iros_llm_orchestrator install/iros_llm_orchestrator
colcon build --packages-select iros_llm_orchestrator
```

Важно понимать почему это не мелочь: `config/orchestrator.yaml` и `launch/`
ставятся **копированием**, а не ссылкой. Пока пакет не пересобран, правки в
исходниках не влияют ни на что — стек поднимется со старыми значениями и без
OpenRouter в белом списке, и выглядеть это будет как «инструкция врёт».

### 1.4 Проверка перед сменой

```bash
# ключ жив, лимит на месте
curl -s -H "Authorization: Bearer $LLM_API_KEY" https://openrouter.ai/api/v1/key

# провайдер сегодня отвечает (ждём 200)
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  https://openrouter.ai/api/v1/chat/completions \
  -H "Authorization: Bearer $LLM_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"qwen/qwen3.5-397b-a17b","messages":[{"role":"user","content":"hi"}],
       "max_tokens":1,"provider":{"order":["Chutes"],"allow_fallbacks":false}}'
```

Если провайдер отдаёт не 200 — взять другой **fp8 с поддержкой инструментов**
(DeepInfra, Parasail, AtlasCloud, GMICloud) и записать замену. **DigitalOcean
не брать**, несмотря на цену: 36 с на вызов перекрывают бюджет миссии (§4.3).
Менять провайдера посреди кампании нельзя — только перегонять всё (§4.6).

## 2. Что ставится в каждом прогоне

Один флаг — одна ячейка. Всё остальное зашито:

```bash
bash /home/fabian/ros2_ws/src/scripts/easy_record.sh --B
```

Больше ничего набирать не нужно. Обёртка сама:

- подставляет точку входа, модель, провайдера и флаги абляции этой ячейки;
- **считает номер повтора** по уже записанным сессиям — помнить, третий это
  прогон или четвёртый, не надо;
- **печатает текст миссии** для вставки в панель RViz;
- для ячеек со вторым окном (`M2d`, `no-LLM`) печатает, что и когда там
  запускать.

Посмотреть список ячеек и проверить команду, не поднимая стек:

```bash
bash .../easy_record.sh --list
bash .../easy_record.sh --M2d --dry-run
bash .../easy_record.sh --B --rep 3      # если нужен конкретный номер
```

**Почему обёртка, а не набор флагов руками.** Ячейки B, B-M1, B-M3 и M4
запускаются **побайтово одинаковыми** флагами и различаются только миссией,
которую печатает оператор. Ошибиться в `--cell` было легко, а заметить потом —
нечем: факторы, модель и планировщик у них совпадают. Здесь имя ячейки выбирает
флаги, так что разойтись они не могут.

Внутри обёртка вызывает `record_session.sh` — он и пишет `session.json`, куда
`cell`, `mission` и `repeat_index` ложатся **отдельными полями**, а не внутрь
свободного текста. По ним группируется разбор.

## 3. Таблица сценариев

Модель, планировщик (`lns`), карта (`amongus`) и 20 роботов — одинаковые везде,
кроме явно указанного. Тексты миссий — в §4, копировать побайтово.

| # | команда | что проверяет | миссия | прогонов |
|---|---|---|---|---:|
| 1 | `--B` | опорная точка: система целиком, все страховки включены | M2 | 5 |
| 2 | `--no-remediation` | нужен ли перепромпт после отказа исполнения | M2 | 5 |
| 3 | `--no-repair` | нужна ли постпроверка и починка результата | M2 | 5 |
| 4 | `--no-supervision` | нужен ли цикл выполнить→проверить→продолжить | M2 | 5 |
| 5 | `--constrained` | режим планирования: схема вместо инструментов | M2 | 5 |
| 6 | `--model-9b` | размер модели: то же семейство, в 44 раза меньше | M2 | 5 |
| 7 | `--no-LLM` | потолок субстрата: заведомо правильный план без модели | M2 | 5 |
| 8 | `--M2d` | починка: дверь ломает маршрут, обход остаётся | M2 | 5 |
| 9 | `--PBS` | взаимозаменяемость планировщиков | M2 | 5 |
| 10 | `--M4` | строй: две защиты из шести + точность удержания | M4 | 5 |
| 11 | `--B-M1` | нижний край сложности | M1 | 3 |
| 12 | `--B-M3` | верхний край сложности | M3 | 3 |

**Порядок прогонов — вперемешку, не блоками.** Пять повторов базы подряд утром
и constrained вечером дадут разницу частично про машину и загрузку провайдера.

### Особые ячейки

Обёртка сама печатает всё нужное при запуске — ниже то же самое, чтобы знать
заранее.

**6 — `--model-9b`.** Chutes девятку не раздаёт. Прибить SiliconFlow, DeepInfra,
Venice или Together; **Parasail не годится — не поддерживает инструменты**.
Обёртка предупредит об этом на старте и запишет фактического провайдера.

**8 — `--M2d`.** Оператор печатает **тот же текст M2**. Через 60 с обёртка
попросит закрыть дверь во втором окне.

**Дверь ещё не выбрана.** Прежняя подбиралась под старый набор плеч и с новым
M2, вероятно, ни на что не влияет. До сбора данных по этой ячейке нужен замер
по occupancy grid: дверь должна ломать **ровно одно** плечо и **оставлять
обход**. Наглухо перекрывать нельзя — субстрат этого не переживает достаточно
тихо, чтобы мерить решение модели, и запись покажет развал Nav2 и LNS2, а не
работу оркестрации. Обёртка на старте об этом предупреждает.

**7 — `--no-LLM`.** В панель не печатается ничего, миссию ведёт
`e3_scripted_driver` из второго окна. `WARNING: no channel-3 records` в финале
здесь правильный — для остальных ячеек это брак.

**10 — `--PBS`.** Отдельной подготовки больше не требует: дефект
`time_step_sec: 0.1` исправлен в `mapf.launch.py`.

## 4. Тексты миссий

Оператор печатает это в чат-панель RViz. **Побайтово, без переписывания** —
любая правка делает прогоны несравнимыми.

**M1** — лёгкая, две точечные задачи, четыре робота:

```
Send one magenta robot and one orange robot to the electrical task at (-6.31, -3.66). Send one orange robot and one yellow robot to the communications task at (7.84, -15.76).
```

**M2** — рабочая, пять плеч, все пять групп по двое, смешанные пары, одна
переноска. Идёт в ячейках 1–9:

```
Send one magenta robot and one orange robot to the electrical task at (-6.31, -3.66). Send one cyan robot and one orange robot to the med task at (-6.84, 1.37). Send one yellow robot and one green robot to the hall task at (-2.58, 16.10). Send one yellow robot and one green robot to the communications task at (7.84, -15.76). Send one cyan robot and one magenta robot to carry the security cargo: first to the pickup at (-15.99, 3.65), then to the dropoff at (12.29, -5.06).
```

**M3** — тяжёлая, все девять задач:

```
Complete all declared tasks.
```

**M4** — строй:

```
Form a column of four cyan robots led by robot_0 in the cafeteria at (2.7, 10.1), then move the column to storage at (0.6, -10.9), then disband it.
```

## 5. Ячейка no-LLM

Единственная, которая **не ходит в сеть**. В панель ничего не печатается,
миссию ведёт скрипт.

```bash
# окно 1
bash .../easy_record.sh --no-LLM

# окно 2, после того как стек поднялся
docker compose exec terminal bash
source /home/fabian/ros2_ws/install/setup.bash
source /home/fabian/ros2_ws/src/scripts/setup_swarm_env.sh
ros2 run iros_llm_swarm_bt e3_scripted_driver          # миссия M2
```

Водитель берёт цели из `/tasks/list`, а не из констант, и ведёт переноску в два
захода — сначала погрузка, потом ожидание статуса `carrying`, потом разгрузка.
Порядок принципиален: менеджер закрывает переноску только по прибытию того
робота, которого запомнил на погрузке (`E3_spec.md` §2).

Проверить, что сценарий объявляет нужные задачи, до подъёма всего стека:

```bash
ros2 run iros_llm_swarm_bt e3_scripted_driver --dry-run   # нужен менеджер задач
```

В финальном блоке скрипт напишет `WARNING: no channel-3 records` — **здесь это
правильно**. Для всех остальных ячеек это брак.

## 6. Пилот: пять прогонов базы до начала сетки

Не пропускать. Шесть проверок (§6 спеки):

| # | что | если не так |
|---|---|---|
| 1 | выполнение строго между 0 и 100% | 5/5 успехов — миссия лёгкая, рабочей делать M3; 0/5 — чинить стек |
| 2 | хоть одна страховка сработала | иначе вся сетка даст семь одинаковых чисел |
| 3 | миссия заметно короче 600 с | поднимать бюджет |
| 4 | модель реально зовёт инструменты | один вызов на миссию = tool-calling-арм фиктивен |
| 5 | **ноль транспортных отказов** | не гнать сетку, разбираться с провайдером |
| 6 | медиана `llm_seconds` < половины бюджета | резать `tool_max_iterations` до 12 и переснять пилот |

Пилотные прогоны засчитываются как первые пять повторов базы, **если после них
конфигурацию не трогали**. Тронули — выбрасывать и гнать базу заново.

## 7. Годен ли прогон

Проверять сразу после прогона, не копить до конца кампании.

1. Скрипт не написал `RUN FAILED`.
2. В `session.json` факторы, модель и провайдер — те, что задумано.
3. Ровно одна запись в `llm_chat/*.jsonl` (для no-LLM — ни одной).
4. Все 20 роботов поднялись и Nav2 активен **до** подачи команды.
5. Никакого ручного вмешательства — кроме ячеек 8 и 9, где дверь закрыта на
   60-й с ±5 с и роботы сломанного плеча её ещё не прошли.
6. Не больше 8 минут от команды. Дольше — записать как **незавершённый**, не
   выбрасывать.
7. **Ни одного транспортного отказа**: в журнале нет `HTTP 4xx`, `HTTP 5xx`,
   `Access denied by security policy`, `rate-limited upstream`.

Пункт 7 — единственное, что перегоняется. Разница принципиальная и её легко
перепутать:

> **Модель отказалась, ошиблась или не уложилась — это данные, их сохраняют.
> Запрос не дошёл до модели — это не данные, прогон переигрывают.**

Различаются только по тексту ошибки в журнале. Число перегонов по пункту 7
записывать: если оно велико, это характеристика сервиса, и её надо назвать в
ограничениях статьи.

Провалившийся прогон записывается как провалившийся, с причиной. Молча
переделывать нельзя — доля отказов одно из чисел, ради которых всё делается.

## 8. Что отдавать

Папку `paper/results/sessions/<метка времени>/` целиком, не выборочно.

| файл | без него нельзя |
|---|---|
| `bag/` | считать выполнение, время, пробег |
| `session.json` | понять, какая это ячейка и на чём гонялась |
| `llm_chat/*.jsonl` | посчитать вызовы модели, срабатывания страховок, отказы |
| `llm_decisions/`, `llm_commands/` | материал для E3b |
| `launch.log` | разобрать упавший прогон |

Половина метрик живёт **только** в `llm_chat/` и никуда не публикуется. Папка
без него бесполезна для половины эксперимента.
