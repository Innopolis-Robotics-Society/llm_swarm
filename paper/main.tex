\begin{abstract}
We present \code{iros\_llm\_swarm}, a complete ROS~2 system in which a large
language model supervises a 20-robot differential-drive swarm from free-form
natural language. Unlike prior LLM-robotics work that emits low-level code or
single-robot skill sequences, our orchestration layer emits a \emph{typed,
recursive plan tree} over four fleet-level primitives and two control
containers, and every leaf is
discharged by a classical algorithm --- Multi-Agent Path Finding (MAPF) with
two interchangeable backends (PBS and LNS2), a centralized leader--follower
formation manager, and a BehaviorTree.CPP mission front-end. The LLM therefore
never touches velocities, trajectories, or conflict resolution; it is confined
to a small, well-typed decision surface that the underlying stack can validate,
reject, and repair.

The contribution of this paper is the orchestration layer and its evaluation
methodology. We describe three control channels (reactive, proactive, and
operator chat), a grounding stack that gives the model bounded access
to live fleet state through eight semantic tools, schema-constrained decoding
against the plan grammar, and---centrally---a \emph{defence-in-depth} design in
which six deterministic guards and three LLM-in-the-loop repair loops sit
between a generated plan and the robots. We further contribute a reproducible
evaluation design: a 44-case hermetic planning benchmark spanning twelve
structural categories, and a proximity-driven task system that
turns end-to-end mission success into an automatically scored quantity, so that
planning accuracy and mission completion can be measured separately and
attributed to individual architectural components by ablation.

Measuring those components turned up a result we did not set out to find.
Schema-constrained decoding, the first guard in the chain, destroys planning
on one of the six models tested under it---a 68-point drop with eight of
twelve plan categories at exactly zero---and a schema ladder locates the fault
in branch \emph{selection} rather than in recursion or in filling a branch:
the model alphabetises its keys in schema mode, so a \code{oneOf} discriminated
by a trailing \code{type} field must be committed on a content key before the
type is named. Re-running both arms against four hosted models shows the
convention is one model's and the other five are unharmed, but also that
whether it is expressed at all is decided by the decoding engine: the same
weights alphabetise on every node under one runtime and a minority under
another, passing 24\% or 91\% of calls accordingly.

\pending{This draft fixes the system description and the experimental design.
E1 (hermetic planning accuracy) is populated across five local models, E2
(grounding and constraint ablation) across three, and E2c (hosted reference
sweep) across four; E3 remains unpopulated pending further runs.}
\end{abstract}

\section{Introduction}

Coordinating a fleet of mobile robots that share one workspace is a long-standing
problem. The classical decomposition separates fleet-level decisions---which
robot goes where, in what order---from robot-level execution---how one robot
follows a path or holds an offset. Large language models make this decomposition
newly attractive~\cite{saycan,codeaspolicies,progprompt,innermonologue}: an LLM
can reason over compact semantic primitives instead of producing control
commands, while the classical stack retains responsibility for safety, conflict
resolution, and real-time tracking.

The difficulty is that this promise is easy to state and hard to make hold. A
language model asked to command twenty robots will confidently emit coordinates
inside walls, address robots that are currently locked into a formation, place
four robots on the same point, invent room names, and return JSON that does not
parse. Any one of these silently produces a fleet-wide failure. The engineering
question this paper addresses is therefore not \emph{can an LLM plan for a
swarm} but \emph{what has to sit between the LLM and the robots so that it
can}, and how much each of those pieces is actually worth.

\subsection{Scope and contributions}

We study a fleet of 20 differential-drive robots in a 2D environment simulated
with Stage, each running its own Nav2 stack. The system spans three layers: a
natural-language orchestration layer (this paper's focus), a classical
coordination substrate (MAPF, formations, behavior trees), and per-robot
navigation. Our contributions:

\begin{enumerate}[label=(\arabic*)]
\item \textbf{A typed plan language for fleet control.} Four leaf primitives
(\code{mapf}, \code{formation}, \code{disband}, \code{idle}) and two containers
(\code{sequence}, \code{parallel}) form a recursive tree that is expressive
enough for multi-group, multi-phase missions yet small enough to be validated
exhaustively and to be expressed as a JSON schema for constrained decoding
(Sec.~\ref{sec:planlang}).

\item \textbf{Three orchestration channels} over one substrate: a reactive
channel invoked by behavior-tree nodes on WARN/ERROR, a proactive channel that
observes fleet state and intervenes on its own initiative, and an operator chat
channel that streams a reply and an executable plan (Sec.~\ref{sec:channels}).

\item \textbf{A grounding stack} that replaces coordinate hallucination with
lookup: a live pose cache, a room-occupancy-aware group placement solver, and
eight semantic tools brokered behind an allowlist (seven read-only), with an
optional MCP provider for raw ROS introspection (Sec.~\ref{sec:grounding}).

\item \textbf{Defence in depth between plan and robots}: six layers---schema-constrained decoding, a schema validator, permissive type coercion,
an active-formation guard, an occupancy-aware goal rewriter, and automatic
formation staging---all deterministic, none requiring another model call
(Sec.~\ref{sec:guards}).
Sec.~\ref{sec:res-e2} shows the first of these is also the one that can do the
most damage, which is an argument for the other five rather than against the
principle.

\item \textbf{A bounded closed loop}: deterministic post-execution
verification feeding three nested LLM repair loops (remediation, verification
repair, mission supervision), each with an explicit step, time, and
no-progress budget (Sec.~\ref{sec:closedloop}).

\item \textbf{A 20-robot execution substrate} that makes the above runnable and
measurable: a Stage 2D environment reached after a documented pivot from Gazebo
Harmonic, five scenarios with symbolic map descriptions and a dynamic obstacle
system, per-robot Nav2 stacks generated from a single parameter template with
staggered bring-up, and a static-localization strategy that replaces AMCL at
this fleet density (Sec.~\ref{sec:substrate}).

\item \textbf{A reproducible evaluation design} (Sec.~\ref{sec:expdesign}) that
separates planning competence from execution competence, scores end-to-end
missions automatically via a proximity-driven task system, and attributes
outcomes to individual components through configuration-level ablation.
\end{enumerate}

The system was drafted internally as two partial write-ups organised around a
three-level split of the work: one covering the classical coordination
substrate, the other the simulation environment, per-robot navigation, and an
early design of the orchestration layer. Each necessarily described its layer
against \emph{assumed} interfaces at the boundary. This paper is the unified
account of the system as built: it supersedes both drafts, corrects the
orchestration-layer description to match the shipped implementation,
and---because planning quality and mission success can only be compared on the
whole stack---evaluates the three layers together rather than separately.

\section{Related Work}

\paragraph{Multi-Agent Path Finding.}
MAPF has a rich algorithmic literature~\cite{stern}. Conflict-Based
Search~\cite{cbs} is the canonical optimal solver. Priority-Based Search
(PBS)~\cite{pbs} relaxes optimality for scalability: a strict priority ordering
replaces time-indexed constraints, and each agent plans deterministically
against higher-priority paths. Large Neighborhood Search for MAPF
(LNS2)~\cite{lns2} is anytime and suboptimal, starting from a possibly
colliding plan and iteratively destroying and repairing agent subsets with
soft-constraint A*. We adopt both behind one action interface, which lets us
treat the backend as an experimental factor rather than a design commitment.

\paragraph{Formation control.}
Formation control is typically posed as leader--follower, virtual structure, or
behavior-based~\cite{formsurvey1,formsurvey2}, with potential-field and
sliding-mode variants for continuous inter-robot spacing~\cite{apf}. We use
leader--follower because it composes cleanly with a per-robot motion controller
and matches the kind of semantic offset (``a wedge'', ``abreast'') a language
model naturally produces.

\paragraph{Navigation and behavior trees.}
Nav2~\cite{nav2} is the de facto ROS~2 navigation stack, with layered
costmaps~\cite{layered} the standard obstacle representation. Behavior
trees~\cite{btbook,btsurvey} via BehaviorTree.CPP~\cite{btcpp} provide a modular
control architecture that is particularly suitable when an external reasoning
component supplies tree parameters.

\paragraph{LLMs for robotics.}
The area is broad enough to have its own surveys~\cite{llmrobsurvey}. SayCan~\cite{saycan}
grounds language in affordances; Code as
Policies~\cite{codeaspolicies} and ProgPrompt~\cite{progprompt} emit executable
program text; end-to-end vision-language-action models such as
RT-2~\cite{rt2} go further and regress actions directly, which trades away
exactly the inspectable intermediate representation we rely on; Inner
Monologue~\cite{innermonologue} closes the loop with
textual feedback. Our design differs in two respects that matter at fleet
scale. First, the model emits a \emph{typed tree over fleet primitives}, not
code: the output space is small enough to constrain by schema and validate
exhaustively, which removes the arbitrary-code-execution surface and the
malformed-output failure mode. Second, feedback is not free text but a
\emph{deterministic verification record} computed from formation status and
pose state (Sec.~\ref{sec:closedloop}), so the repair loop is driven by
measured ground truth rather than by the model's own narration.

\paragraph{ROS~2 and DDS at scale.}
ROS~2~\cite{ros2} places DDS on the critical path, and discovery cost dominates
at scale~\cite{dds1,dds2}. We use CycloneDDS with
a project-specific profile; without it the 20-robot system does not reliably
complete discovery within the launch budget.

\section{The Classical Substrate}
\label{sec:substrate}

This section summarizes the layer the orchestrator commands.

\paragraph{Shared fleet action.}
Both MAPF backends own the same long-lived \code{/swarm/set\_goals} action,
which encapsulates the entire
$\textit{validating} \rightarrow \textit{planning} \rightarrow
\textit{executing} \rightarrow \textit{replanning} \rightarrow
\textit{succeeded}$
lifecycle behind one goal token. Schedule monitoring and replanning are
internal; clients see one atomic operation. Cancellation stops every robot. The
action result carries a full metrics payload---planning time, node expansions,
per-agent path lengths, replan count, total execution time---which we exploit
directly for benchmarking (Sec.~\ref{sec:e3}).

Because the contract is shared, the backend is a launch-time switch and nothing
above it changes: the orchestrator, the guards, the behavior tree, and the
per-robot followers are all written against the action, not against a solver.
E3 runs the same mission workload on both backends, which is the evidence we
offer for that interchangeability. It is deliberately \emph{not} a comparison of
the two solvers---see Sec.~\ref{sec:folded} for why we do not make one.

\paragraph{PBS backend.}
An 8-connected A* on a grid downsampled to 0.2\,m, with a backward-Dijkstra
heuristic per unique goal, two-zone gradient inflation (hard footprint plus a
soft penalty zone), and capsule-vs-capsule conflict detection that subsumes the
usual vertex/edge split. The high-level search follows the priority-based
formulation of~\cite{pbs}.

\paragraph{LNS2 backend.}
An initial soft-constraint A* solution refined by an adaptive
large-neighborhood search with four destroy operators (collision-based,
random-walk, random, bottleneck) whose weights adapt online. It is anytime,
tolerant of transiently infeasible starts, and warm-starts on replan.

\paragraph{Per-robot followers and formations.}
Each robot runs a dual-mode follower: in AUTONOMOUS mode it dispatches its
assigned plan to Nav2 \code{follow\_path}; in FORMATION mode it disengages Nav2
and runs a PD controller tracking
$p_{\mathrm{ref}} = p_{\mathrm{leader}} + R(\theta_{\mathrm{leader}})\,o$
for a body-frame offset $o$. Mode switching is driven by a single latched
message, without node restarts. A centralized manager owns formation
definitions and republishes the full registry on a latched topic; a monitor
computes per-follower error
$\varepsilon_i = \lVert p_i - (p_{\mathrm{leader}} + R(\theta_{\mathrm{leader}}) o_i) \rVert$
and classifies each formation as INACTIVE / FORMING / STABLE / DEGRADED /
BROKEN at 10\,Hz. These $\varepsilon_i$ are published, which makes formation
tracking accuracy directly measurable (Sec.~\ref{sec:folded}).

\paragraph{Behavior-tree front-end.}
BehaviorTree.CPP v3 nodes wrap every primitive: \code{MapfPlan},
\code{SetFormation}, \code{DisableFormation}, and a \code{CheckMode} guard.
Mission completion is observed on the \code{/bt/state} blackboard mirror, whose
\code{active\_action} field cycles \code{none} $\rightarrow$ node $\rightarrow$
\code{none}; the orchestrator keys leaf completion on this transition rather
than on the command acknowledgement, which is only an ack.

\paragraph{Simulation environment.}
The fleet runs in Stage 2D~\cite{stage} via \code{stage\_ros2}, with a unified
TF tree and enforced namespace prefixes. An earlier Gazebo
Harmonic~\cite{gazebo} configuration was implemented end-to-end and then
retired: per-robot physics, collision broadphase, and sensor rendering pushed
the real-time factor below usable thresholds at 20 robots before any navigation
stack was attached. The Gazebo configuration is retained in
tree for smaller fleets and future hardware-realistic preview.

Five scenarios share one robot model and spawn protocol: \textsf{cave}
(75$\times$75\,m, narrow single-file passages), \textsf{large\_cave}
(150$\times$150\,m, same topology at double scale), \textsf{warehouse\_2} and
\textsf{warehouse\_4} (30$\times$30\,m, two- and four-group symmetric layouts),
and \textsf{amongus} (66.6$\times$37.75\,m), which maps the spaceship layout of
\emph{Among Us: The Skeld} into 14 named rooms joined by narrow corridor
choke-points. We use \textsf{amongus} for all orchestration experiments because
its rich naming exercises symbolic reference and its choke-points stress
conflict resolution.

Each scenario ships a machine-readable map description consumed by the
orchestrator: named locations with coordinates, aliases in English and Russian,
colour-coded robot groups with home and spawn positions, formation-capable
zones with free-space radii, and map-specific planning heuristics (bottleneck
locations, known-unreachable goal patterns, abort-versus-replan guidance). A
dynamic obstacle manager additionally supports runtime-togglable doors and
placeable obstacles; \textsf{amongus} declares six corridor doors matching the
map geometry.

\paragraph{Scale engineering.}
Three decisions are load-bearing at 20 robots and are reported because they
constrain the experiments. CycloneDDS with a custom profile is mandatory above
roughly ten participants. AMCL is disabled---each robot's scan contains every
other robot's body, and particle weights collapse---so localization is a static
per-robot \code{map} $\rightarrow$ \code{odom} identity transform over simulator
odometry. Bring-up is staggered (simulator 0\,s, Nav2 1\,s, planner 10\,s,
followers 12\,s, plus 0.3\,s per Nav2 instance).

\section{Orchestration Layer}

\subsection{Three channels}
\label{sec:channels}

The orchestrator exposes three independent paths from language to fleet action,
which share prompt infrastructure and the plan validator but differ in trigger,
latency budget, and authority.

\textbf{Channel~1 (reactive).} A \code{/llm/decision} action server. Behavior-tree
nodes call it when a primitive reports WARN or ERROR, supplying the event plus a
tail of the accumulated log. The model returns exactly one of
\code{wait} / \code{abort} / \code{replan}. The prompt biases hard toward
\code{wait} and enumerates planner-internal warnings that indicate
\emph{self-recovery in progress} (``replan did not reach collision-free; keeping
old paths'', ``warm seed rejected'') as explicit \code{wait} cases---because
the expensive error here is a spurious \code{replan} that cancels a plan the
substrate was about to fix on its own. Always active.

\textbf{Channel~2 (proactive).} A passive observer subscribing to
\code{/bt/state}. It decides on its own initiative whether to intervene and
publishes an \code{LlmCommand} that a behavior-tree receiver applies to the
blackboard. It is cooldown-gated and checks an \code{llm\_thinking} flag to
avoid colliding with channel~1. Off by default.

\textbf{Channel~3 (operator chat).} The main path, and the focus of this paper.
An operator types free-form text; the server streams a natural-language reply
token-by-token, parses an executable plan from the same response, and dispatches
it. Everything in Secs.~\ref{sec:planlang}--\ref{sec:closedloop} describes
channel~3.

\subsection{Plan language}
\label{sec:planlang}

Channel~3 returns a single JSON object \code{\{reasoning?, reply, plan\}}, where
\code{plan} is a recursive tree over the node types in
Table~\ref{tab:planlang}.

\begin{table}[t]
\centering\small
\caption{Plan tree node types.}
\label{tab:planlang}
\begin{tabular}{@{}llp{4.1cm}@{}}
\toprule
\textbf{Node} & \textbf{Kind} & \textbf{Payload / semantics} \\
\midrule
\code{mapf}      & leaf & \code{robot\_ids}, \code{goals}, \code{spread}; one goal per robot, or one centre that the server grids \\
\code{formation} & leaf & \code{formation\_id}, \code{leader\_ns}, \code{follower\_ns}, \code{offsets\_x/y} \\
\code{disband}   & leaf & \code{formation\_id} \\
\code{idle}      & leaf & \code{reason}; also the carrier for escalation (see below) \\
\code{sequence}  & container & children in order; abort on first failure \\
\code{parallel}  & container & see flattening rules below \\
\bottomrule
\end{tabular}
\end{table}

Three design decisions in this grammar are worth stating explicitly.

\emph{Parallelism is a claim about intent, not about threads.} A
\code{parallel} node is flattened before execution: multiple \code{mapf} leaves
\emph{merge into one} \code{mapf} goal, because the MAPF planner already
resolves inter-robot conflict internally and issuing two concurrent fleet goals
would defeat exactly the coordination we want. Mixed \code{mapf} and
\code{formation} children degrade to sequential execution, since a formation
requires its own follower mode. An \code{idle} in any branch short-circuits the
whole node---stop takes priority. This means the operator's ``do A and B at the
same time'' is honoured as \emph{one jointly planned motion}, which is stronger
than concurrent dispatch, not weaker.

\emph{\code{idle} doubles as the escalation channel.} Rather than adding node
types for ``I need clarification'' and ``here is an answer, no action needed'',
the model emits \code{idle} with a prefixed reason: \code{needs\_help:},
\code{clarify:}, or \code{reply\_only:}. This keeps the grammar at six node
types---small enough to constrain by schema---while still distinguishing
refusal-to-act from action. It also makes escalation a first-class, testable
behaviour: a benchmark case can assert that a question with a missing robot
pose produces \code{needs\_help:} and not a confident plan over stale data.

\emph{The schema is enforced twice.} \code{plan\_schema.py} expresses the
grammar as a JSON schema with a recursive \code{\$defs/node} reference, passed
to the backend for constrained decoding (Ollama \code{format}, OpenAI
\code{response\_format}). But JSON Schema cannot express the cross-field
constraint $|\code{goals}| = |\code{robot\_ids}|$, so a hand-written validator
re-checks every node after parsing. Constrained decoding removes the
\emph{malformed} failure mode; the validator removes the \emph{incoherent} one.

\subsection{Grounding}
\label{sec:grounding}

A model asked for ``cyan to the cafeteria'' must resolve a colour group to
robot ids, a room name to coordinates, and coordinates to free floor space. We
push all three out of the model's head and into lookup.

\emph{Static context.} The prompt carries a per-map description: named
locations with coordinates, colour groups with member ids and home positions,
formation-capable zones with radii, and door geometry. Maps are declared in
\code{common\_scenarios.yaml}, so adding an environment does not touch the
orchestrator.

\emph{Live context.} A pose cache subscribes to \code{/robot\_*/odom} and
supplies fresh positions with an explicit staleness bound (2\,s). This is what
lets the model compute formation goals as $\textit{leader}_{xy} + \textit{offsets}$
rather than inventing absolute coordinates---and, equally important, lets it
\emph{notice a missing robot} and escalate instead of planning over a gap.
Formation status, behavior-tree state, recent events, and open task state are
folded into the same snapshot under a character budget.

\emph{Semantic tools.} Eight tools sit above raw introspection.
\code{get\_robot\_position} returns one robot's live map-frame pose;
\code{get\_positions} resolves named geometric points such as room corners,
doorways and choke-points; \code{check\_occupancy} returns the local occupancy
grid around a robot, built from its lidar.
\code{find\_free\_group\_goals\_in\_room} computes deterministic
occupancy-aware per-robot goals for ordinary group movement, and
\code{find\_group\_placement\_in\_room} the non-overlapping leader/follower
placements a formation needs. \code{verify\_plan\_execution\_state} checks
post-execution formation state and follower offset errors. \code{list\_tasks}
and \code{reset\_task} read and write the task ledger. They are dispatched
by a broker that enforces an allowlist, a per-round tool cap, a timeout, and a
result-size cap. An optional MCP provider (\code{ros-mcp} over stdio) adds raw
ROS introspection under a separate eleven-verb allowlist restricted to reads.
The model never sees MCP tools directly---only a bounded snapshot or a brokered
semantic call.

Seven of the eight are read-only; \code{reset\_task} is the exception, and it is
worth naming rather than glossing. It returns a task to \code{pending} so a
stuck or mis-scored task can be retried, which mutates the same task state that
Sec.~\ref{sec:tasks} uses to score missions. The write surface is therefore
narrow and confined to the task ledger---no tool commands a robot---but it is
not empty, and an evaluation that scores itself from task state should not
expose a tool that can rewrite it. We flag this as a defect of the current
allowlist rather than a property of the design.

This is the learned-tool-use pattern of Toolformer~\cite{toolformer} applied
under a broker rather than in the open: the model chooses among a fixed,
audited set instead of inventing calls.

Notably, tool calling and schema-constrained decoding are \emph{mutually
exclusive} in current backends: constrained decoding suppresses tool-call
emission. The system therefore has two distinct planning modes, which we treat
as a primary experimental factor (Sec.~\ref{sec:e2}).

\subsection{Defence in depth}
\label{sec:guards}

Table~\ref{tab:guards} lists what stands between a generated plan and the
robots. The design principle is that \emph{a deterministic guard is always
preferred to another model call}: guards are cheap, reproducible, and cannot
themselves hallucinate.

\begin{table}[t]
\centering\small
\caption{Layers between a generated plan and the fleet. D = deterministic,
L = requires an LLM call.}
\label{tab:guards}
\begin{tabular}{@{}llp{3.5cm}@{}}
\toprule
\textbf{Layer} & & \textbf{Failure mode addressed} \\
\midrule
Constrained decoding      & D & unparseable / off-grammar JSON \\
Schema validator          & D & structurally valid but incoherent nodes \\
Type coercion             & D & \code{"robot\_10"} where an \code{int} is required \\
Active-formation guard    & D & direct MAPF control of a robot locked in a live formation \\
Occupancy rewrite         & D & room-centre goals that land in walls or clump \\
Formation prestaging      & D & bare \code{formation} leaf with followers out of position \\
\midrule
Remediation loop          & L & execution failed; replan with failure briefing \\
Verification repair       & L & execution reported success but the outcome does not hold \\
Mission supervision       & L & multi-step mission needs continuation \\
\bottomrule
\end{tabular}
\end{table}

Two of these deserve elaboration because they encode domain knowledge the model
does not reliably have.

\emph{Type coercion} is deliberately permissive. Small local models routinely
emit \code{"robot\_10"} or \code{10.0} where the grammar wants \code{10}. A
strict parser would reject an otherwise perfect plan over a namespace string.
The coercer accepts \code{10}, \code{"10"}, \code{"robot\_10"},
\code{"robot10"}, and integral floats, while explicitly rejecting booleans
(which are \code{int} subclasses in Python and would otherwise silently become
robot~0 or~1). Strictness is spent where it buys safety, not where it only
punishes formatting.

\emph{The active-formation guard} exists because ``send the magenta line to
storage'' is ambiguous in a way that matters. A formation is commanded by moving
its \emph{leader}; commanding all four members individually tears it apart. The
guard reads live formation status, and for any formation in FORMING, STABLE, or
DEGRADED it strips follower ids out of MAPF leaves, leaving the leader. It
returns a structured failure record shaped exactly like a PlanExecutor failure,
so the existing repair loop consumes it with no special handling.

\subsection{Closed loop}
\label{sec:closedloop}

Execution success is not the same as mission success, and this distinction
drives the whole loop design. A plan can execute cleanly---every action server
returns success---while the requested outcome does not hold: robots arrive but
the formation never stabilizes, or they arrive at a room's centre and pile up.
The system therefore verifies deterministically after execution, reading
formation status and pose state to decide whether what was asked for is
actually true, and emits an honest \emph{partial} result when state is missing
rather than guessing.

Three nested loops consume that verdict, each explicitly budgeted:

\begin{itemize}
\item \textbf{Remediation} (default 2 attempts) fires when execution
\emph{fails}. It re-prompts with the failed leaf, the error, the history of
prior attempts, and a \emph{targeted refresh} of runtime context---not the full
snapshot, to keep the retry prompt inside the context budget.
\item \textbf{Verification repair} (default 2 attempts) fires when execution
\emph{succeeds} but verification says the outcome does not hold, and only when
the verifier itself marks the discrepancy repairable.
\item \textbf{Mission supervision} (default 6 steps, 180\,s) wraps both in a
bounded execute--verify--continue loop for multi-phase missions, with a
no-progress limit of 2 and a fingerprint set of already-failed plans so the
model cannot loop on a plan that has already been tried.
\end{itemize}

Every loop terminates in a help escalation to the operator rather than in
silent failure or unbounded retry. We regard these budgets as tuning
parameters, not constants, and measure their effect directly
(Sec.~\ref{sec:e3}).

\subsection{Task system as mission ground truth}
\label{sec:tasks}

A separate node maintains a set of spatial tasks and polls TF at 5\,Hz. A
\emph{point} task transitions PENDING $\rightarrow$ DONE when any robot enters
its radius. A \emph{carry} task transitions PENDING $\rightarrow$ CARRYING on
pickup and $\rightarrow$ DONE when the carrying robot reaches the dropoff.
Tasks are declared per scenario in YAML and their state is published.

This component was built for mission planning, but it doubles as the
measurement instrument that makes end-to-end evaluation tractable: it converts
``did the swarm accomplish what the operator asked'' into an automatically
scored, timestamped, operator-independent quantity. Every end-to-end experiment
below is scored from this signal.

\section{Experimental Design}
\label{sec:expdesign}

This section is the methodological core of the paper. We state it in full
before reporting numbers so that the measurement protocol is fixed independently
of its outcome.

\subsection{Research questions}

\begin{description}[leftmargin=2.6em,style=nextline]
\item[RQ1] How accurately does a locally-hosted open-weight LLM translate
free-form fleet commands into valid plans, and how does accuracy vary across
linguistic and structural categories?
\item[RQ2] What does each grounding and constraint mechanism contribute?
Specifically: schema-constrained decoding vs.\ tool calling, live pose context,
and context budget. \emph{Partially answered:} Sec.~\ref{sec:res-e2} reports
the constraint and grounding halves; the comparison against tool calling is
deferred to E3 for the reason given there, so RQ2 is not closed by this draft.
\item[RQ3] Does planning accuracy predict mission success, or does the gap
between them---the part closed by guards and repair loops---dominate?
\item[RQ4] What does each closed-loop layer contribute to end-to-end mission
completion, and at what cost in time and model calls?
\end{description}

An earlier version of this design carried a fifth question---which of the two
MAPF backends is better under identical fleet requests. We have withdrawn it as
a research question rather than answered it narrowly.
Sec.~\ref{sec:folded} gives the reason: the comparison is confounded on this
system in ways parameter alignment cannot fix, and the residue that
\emph{is} measurable---that the orchestration layer completes the same missions
on either backend---is a property of the action contract described in
Sec.~\ref{sec:substrate}, not a question this paper investigates. We report it
there and in E3, and claim nothing about which backend is superior.

RQ3 is the question we consider most important and the one the literature most
often skips: a benchmark measured on plan text alone can look excellent while
the fleet still fails, and the converse---weak plans rescued by strong
guards---is equally possible. Measuring both on the same system is the point.

\subsection{Principle: reuse existing instrumentation}

A deliberate constraint on this design is that it introduces almost no new
measurement code. Every metric below is read from a signal the running system
already produces (Table~\ref{tab:metrics}). This matters for validity: an
evaluation harness that reimplements the notion of success is measuring the
harness, and instrumentation added for a paper tends not to survive the paper.

\subsection{E1: Planning accuracy (hermetic, offline)}
\label{sec:e1}

The 44-case benchmark calls the model directly---no simulator, no ROS---with
\emph{fixed synthetic runtime contexts} (fleet at spawn; a stable magenta line;
a stable cyan wedge; robot~12's pose missing; robot~4 at the cafeteria). Each
case pairs a prompt with a programmatic validator asserting structural
properties of the returned tree: node type, exact robot-id sets, goal proximity
to a named location within a tolerance, goal distinctness, formation leader
identity, staging-before-formation ordering, and escalation-reason prefixes.

Cases span twelve categories chosen to separate distinct competences:
basic single-group \code{mapf}; explicit per-robot coordinates; goal spreading;
\code{parallel} over multiple groups; multi-phase \code{sequence}; formation
creation (which requires \emph{staging followers first and excluding the
leader}); formation movement (which requires commanding \emph{only} the
leader); \code{formation\_complex} (creation followed by a leader-only move);
disband; \code{idle}; escalation under missing or ambiguous state; and a set of
edge cases (repeated/ambiguous commands, partial formations, adjacency
requests). All prompts here are English. An earlier revision of this
benchmark additionally scored reply-language fidelity on a parallel set of
Russian-language prompts; we dropped that set because it tests a UI-level
concern (does the chat reply mirror the operator's language) orthogonal to
planning accuracy, and folding it into a single pass rate obscured both
signals.

\emph{Protocol.} Each case is run $N{=}5$ times per model at temperature 0.1.
We report pass@1 as the mean success rate per attempt over all repeats---220
Bernoulli trials per cell, not 44---and pass@5 as the fraction of cases
solved by at least one of five attempts. The distinction matters and we got
it wrong once: an earlier version of this paper scored pass@1 on the first
repeat only, which estimates the same quantity from a fifth of the data
($\approx\pm6$ points of standard error rather than $\approx\pm3$) and
reported one model at a spurious 100\%, because the first attempt happened to
land on all five of the cases it actually fails most of the time. All figures
below use the mean-over-repeats estimator. We also report per-category breakdown,
end-to-end latency, and the rate of each distinct failure mode (unparseable,
schema-invalid, wrong ids, wrong coordinates, wrong structure). All runs
reported here use \code{--llm-max-tokens 2048} (raised from an initial
768, which was tight enough to make truncated JSON a confound for more
verbose models independent of their planning ability) and
\code{--llm-num-ctx 32768}.

\emph{Models.} The deployment target is a single workstation with 16\,GB VRAM,
which fixes the candidate set. The prompt is large---we measured
$\approx$9{,}700 tokens for the system prompt plus seven few-shot exchanges,
before runtime context---so KV-cache cost is a real constraint, not a rounding
error. We sweep five locally-hosted instruction models spanning that budget:
a small model (\textbf{qwen3.5:4b}, 3.4\,GB); a mid-size model from a
different family (\textbf{gemma3:12b}, 8.1\,GB); the intended 4-bit 14B
operating point (\textbf{qwen2.5:14b}, 9.0\,GB); an 8-bit $\approx$9B model
(\textbf{qwen3.5-9b}, 10\,GB); and the largest model that still fits under the
VRAM ceiling (\textbf{mistral-small3.2:24b}, 15\,GB, 4-bit, partial CPU
offload expected). Whether the last of these remains practical under offload
is itself part of what the latency column reports.

``Intended operating point'' above means the size class we targeted when the
sweep was designed, and it is worth separating from two other senses of
``the deployed model'', because the three do not currently agree.
\code{orchestrator.yaml} ships \code{mistral-small3.1}---a different model from
any swept here, chosen before these measurements existed and never revisited.
E1 then selects \textbf{qwen3.5-9b} on both pass metrics, which is neither the
configured default nor the 14B size class we set out to use. We report the
sweep rather than a single deployment because of exactly this: the
configuration file is not evidence about which model is best, and until E3 runs
end-to-end we treat none of the three as settled. Sec.~\ref{sec:res-e2} shows
why the gap matters beyond bookkeeping---the schema finding is model-specific,
so a stale default is not a harmless one.

\emph{Threat.} E1 measures planning in isolation against synthetic context. It
deliberately cannot detect a plan that is structurally perfect and physically
unexecutable. That is E3's job, and the comparison between them answers RQ3.

\subsection{E2: Grounding and constraint ablation}
\label{sec:e2}

Same harness, same cases, toggling one mechanism at a time:
schema-constrained decoding on/off; live pose context on/off; goal auto-spread
on/off; and context budget swept across its range. These are runtime
parameters of the chat server rather than of the offline harness, and
Sec.~\ref{sec:res-e2} records which of them turned out to be reachable from
the harness at all.

We add one factor that is not currently a parameter: \emph{symbolic versus raw
grounding}. During development we observed that prompting with raw coordinates
produced a higher rate of out-of-bounds and wall-interior goals than symbolic
room references, and that supplying named locations, formation zones, and
map-specific heuristics substantially reduced goal-validation failures
downstream. That observation was uncontrolled and
retrospective. Because the map description is a separable prompt block, it can
be ablated cleanly---full description, locations without heuristics, and
coordinates only---turning an anecdote into a measured effect size. Given that
the map description is a large share of a $\approx$9{,}700-token prompt, this
also quantifies what that context is buying.

One asymmetry must be stated plainly. The offline harness invokes the model
directly and therefore exercises only the plain and schema-constrained paths;
the \emph{tool-calling} path lives in the chat server. Comparing constrained
decoding against tool calling---the mutual exclusivity noted in
Sec.~\ref{sec:grounding}, and arguably the single most interesting ablation
here---therefore requires either extending the harness to route through the
chat server, or measuring that factor only in E3. We initially chose the
first, on the grounds that the second confounds planning mode with execution
noise. In the event we took the second: as reported in
Sec.~\ref{sec:res-e2}, too little of the tool surface is meaningful offline
for the comparison to be worth its apparatus, and the confound we accept in
exchange is stated there.

\subsection{E3: End-to-end missions}
\label{sec:e3}

The primary experiment. A 20-robot stack runs in the 14-location environment
with nine declared tasks (six point, three carry). An operator command is
issued through channel~3; the system plans, executes, verifies, and repairs;
the task manager scores completion independently.

\emph{Factors.} Remediation on/off; verification repair on/off; mission
supervision on/off; planning mode (constrained vs.\ tool-calling); model size;
MAPF backend. The planning-mode factor must be read together with
Sec.~\ref{sec:res-e2}: on
a model that alphabetises keys in schema mode, the constrained arm reproduces
the E2 collapse and E3 would measure that rather than planning mode. The
factor is therefore only interpretable with the model held fixed to one E2
shows is unaffected.

\emph{Mid-mission environment change.} Two cells repeat the reference mission
and close one door of the environment sixty seconds in, chosen so that each
breaks exactly one leg of the plan while the other four keep running as an
in-run control. The first closure lengthens a carry leg from 38\,m to 75\,m: the
route is invalidated but an alternative exists. The second disconnects the
target of another leg outright: no path to it remains at all. This is the case
the repair loops of Sec.~\ref{sec:closedloop} are justified by---the world
changing after a plan is committed---and every other cell exercises them on
execution failures instead. The sharpest quantity is not completion but
escalation: in the disconnected cell, confidently re-planning the same
unreachable goal is an unambiguous failure, while reporting that it cannot be
done, or completing the remaining legs and saying so, is correct. That directly
extends the E1 finding that escalation judgment is weak and flat across model
sizes (Sec.~\ref{sec:e1-results}), by testing it on a live fleet rather than on
plan text. The door state is visible to the model in its per-turn context, so a
failure here is not a failure of information.

\emph{Metrics.} Task completion rate; time to completion; number of LLM calls
per mission (the cost of each safety net); how often each guard fired; how
often each repair loop fired and whether it succeeded; escalation rate; and
total fleet distance travelled.

\emph{Protocol.} $N$ repeats per configuration with a fixed initial fleet
state, resetting task state between runs via the existing reset service.
Because a 20-robot stack is stochastic---DDS timing, Nav2 controller
noise---single runs are not informative, and we report distributions, not
point estimates. This directly addresses a limitation the earlier internal drafts
acknowledged: their integration scenario was run once.

\emph{No-LLM baseline.} The workspace includes a scripted behavior-tree runner
that drives the identical six-step mission---fleet convergence, two formation
activations, a full diagonal cross-swap, return home, idle---against the same
live 20-robot stack with no LLM in the loop. This is
the natural ceiling for E3: it isolates what the substrate achieves when plans
are known-correct by construction. The difference between scripted completion
and LLM-driven completion is precisely the orchestration cost, and reporting
E3 without it would leave the reader unable to tell a weak orchestrator from a
hard environment.

\emph{Guard attribution.} Because guards are deterministic, their contribution
is measurable without disabling them: we log every firing and, for each,
whether the plan would have been physically invalid without it. Disabling a
safety guard on a live 20-robot fleet to measure it is neither necessary nor
wise.

\subsection{E3b: Channel-1 decision accuracy}
\label{sec:e3b}

Channels~1 and~2 are the least evaluated part of the system in either report,
and unlike channel~3 they already write structured per-call JSONL logs
(prompt, raw output, parsed verdict). This makes a replay evaluation nearly
free: accumulate incident records across the E3 campaign, have two
annotators independently label the correct verdict
(\code{wait}/\code{abort}/\code{replan}) from the event and log tail, and score
the model against that label set with inter-annotator agreement reported.

The interesting quantity here is not overall accuracy but the
\emph{asymmetric} error rate. The prompt deliberately biases toward
\code{wait}, because a spurious \code{replan} cancels a plan the substrate was
about to repair on its own, whereas a spurious \code{wait} merely costs one
supervision cycle. We therefore report the confusion matrix rather than a
scalar, and separately the false-\code{replan} rate on the planner-internal
warnings the prompt enumerates as self-recovery cases.

\subsection{Two experiments folded into E3, and why}
\label{sec:folded}

Earlier versions of this design carried two further standalone experiments: a
controlled PBS-vs-LNS2 comparison across fleet size and clutter, and a
formation-tracking study across shape, formation size, and leader speed. Both
are withdrawn as standalone experiments; each survives as one cell of the E3
grid. Because a withdrawal is itself a claim about what can be measured, we
state the reasoning rather than quietly dropping the sections.

\emph{The backend comparison is confounded in ways parameter alignment cannot
fix.} Most differences between the two backends can be equalized by
configuration---grid resolution, planning timestep, arrival tolerance, replan
cooldown, low-level expansion budgets---and we would have. Three cannot. First,
the two solvers terminate on different criteria: LNS2 is bounded by a wall-clock
repair budget and must return the best incumbent it has, whereas PBS is bounded
by high-level node expansions and is not time-bounded at all, so LNS2's planning
time is capped by construction and a head-to-head reading of it is not
meaningful. Second, the collision models differ in kind, not degree: PBS keeps a
hard footprint with a soft gradient penalty zone around it, while LNS2 adds its
inflation directly to the footprint as a hard radius---identically named
parameters with different semantics, which equalizing numerically would hide
rather than remove. Third, the two backends ship with different path-following
stacks, so every execution-side metric measures a planner--follower pair. A
comparison published under those three caveats would say less than the space it
occupies, in a paper whose central question (RQ3) does not depend on it.

What remains is the claim we actually make: the two backends are
\emph{interchangeable} behind one action contract (Sec.~\ref{sec:substrate}).
E3 runs the full mission workload on both, which is evidence for that and for
nothing more. We deliberately do not restate it as a research question: an
outcome of ``the same'' would confirm what the architecture already asserts,
and an outcome of ``different'' would not be attributable, given the three
confounds above. A question whose answers are respectively redundant and
uninterpretable is a system property, and we report it as one.

\emph{Formation tracking becomes a characterization rather than a study.} One
E3 mission forms a column, traverses a 21\,m corridor that narrows to 1.30\,m,
and disbands. The formation monitor already publishes $\varepsilon_i$ at
10\,Hz and E3 already records that topic, so steady-state error, peak error,
time-to-STABLE, and DEGRADED dwell fraction come out of a recording we take
anyway. That mission is also the only one that exercises two of the six
guards---automatic formation staging and the active-formation guard---which
would otherwise report zero firings for the whole campaign for want of a
trigger. What is lost is the dependence of tracking error on shape, size, and
speed: we report one column of four at one speed, and we report it as a
property of this system rather than as a study of formation control.

\subsection{Instrumentation to be added}

Three small additions are required, and we note them explicitly because they
are the only new code the evaluation needs:

\begin{enumerate}[label=(\roman*)]
\item A per-mission JSONL logger on channel~3. Channels~1 and~2 already write
structured logs through a shared writer; channel~3 does not, and E3 cannot be
scored without it.
\item Repeat and machine-readable-output flags on the benchmark harness, which
originally reported only to the terminal and an exit code. \emph{Added}: the
\code{--repeat} and \code{--json} flags used by E1 and E2, together with the
\code{--grounding}, \code{--schema-constrained} and \code{--schema-variant}
factors and a prompt-fingerprint check for baseline reuse.
\item A bag-based offline scorer for E3, in preference to a live scoring
node, so that runs can be re-analysed without re-execution.
\end{enumerate}

\subsection{Threats to validity}
\label{sec:threats}

\emph{Simulation only.} All results are in Stage 2D with simulator odometry as
ground truth and AMCL disabled. Localization error, wheel slip, and real sensor
noise are absent. Conclusions about orchestration transfer more readily than
conclusions about tracking accuracy.

\emph{The simulator pivot is qualitative.} The move from Gazebo to Stage was
driven by observed infeasibility at 20 robots, not by a controlled throughput
sweep. We report real-time factor as a function of fleet size and navigation
load for the Stage configuration only, and make no quantitative claim about the
crossover point. The same applies to bring-up reliability: staggered launch is
observed to work, but failure rate as a function of stagger interval and DDS
profile has not been measured over repeated cold boots.

\emph{Single host.} Twenty robots on one workstation is a DDS-bound ceiling;
timing metrics are contaminated by host load and should be read as relative,
not absolute.

\emph{Benchmark construction.} The 44 cases and the prompt were developed
together by the same authors, which risks the benchmark encoding the prompt's
idiosyncrasies. The category breakdown and the E1/E3 comparison partially
expose this, but we do not claim the benchmark is unbiased with respect to our
own system. An independent case set would be a genuine improvement.

\emph{Model non-stationarity.} Hosted models change under fixed names. We pin
local weights and report quantization for every reported run.

\emph{Environment change is tested by route invalidation, not agent loss.} The
two door cells break the map while every robot keeps working. The complementary
failure---a robot dies while the route stays valid---is not covered, and repair
behaviour may differ between the two: a closed door is visible in the model's
context, whereas a dead robot must be inferred from the absence of motion.

median latency 6$\times$ qwen3.5-9b's---without a corresponding accuracy
gain.

(Table~\ref{tab:e1-failuremodes}). \emph{Wrong formation fields}---almost

shorter than its own follower list---is the single largest failure mode for
three of five models, and for mistral-small3.2:24b it is byte-identical
across 25 of its 47 failures. That repetition, combined with the model's
near-zero pass@1$\to$pass@5 recovery, is the signature of a deterministic
generation bug in how this model fills the formation-node schema, not of
noisy sampling. \emph{Wrong structure} (choosing the wrong top-level node
type, e.g.\ \code{mapf} instead of \code{sequence}) dominates for
qwen2.5:14b (28/55 failures) and gemma3:12b (25/63); qwen3.5:4b has no
single dominant mode, consistent with its noise-like failure profile above.
\emph{Wrong escalation reason} is near-zero for four of the five models,
gemma3:12b being the only one left at 5.

judgment is uniformly hard. The uniformity was real; the explanation was not.

accepting ``either \code{needs\_help:} or \code{clarify:}'' combined two
list-returning validators with \code{or}, an expression that reports an error
whenever \emph{either} prefix is absent---and a reason cannot begin with both.

again, moves 159 calls across E1 and E2. The corrected row says close to the
opposite of the original claim: on the underspecified command \emph{form a
triangle}, all five local models and every hosted model in
Sec.~\ref{sec:res-e2c} emit the byte-identical plan

What differed between them was the prefix, and the prompt's own worked example
is the one that teaches \code{clarify:}. Recognition is uniform and good; only
compliance with an undocumented convention was failing. We record the episode
rather than quietly fixing the number, because a benchmark that cannot be
passed produces exactly the flat profile a real capability gap would.

where the failures cluster, not as precise estimates. We report them because
E2 and E3 (Secs.~\ref{sec:e2}, \ref{sec:e3}) are designed to explain \emph{why}
those specific categories fail, not merely to confirm that they do.

\subsection{E2: Grounding and constraint ablation}
\label{sec:res-e2}

E2 toggles one mechanism at a time against the E1 configuration, on the two
qwen3.5 models: the smallest (\textbf{qwen3.5:4b}) and the most accurate

on/off, and the amount of symbolic scaffolding in the map block

shipped code, checked automatically before each sweep rather than assumed.

32{,}768-token context, 220 calls per cell, 0 timeouts in all seven new

\emph{Schema-constrained decoding buys nothing it was not already needed for,
and reverses sign on one model.} Its purpose is to remove malformed JSON, and
the \emph{unp.} column shows it doing exactly that where the problem exists:
qwen3.5:4b falls from 16 unparseable calls to 1, and both its pass rates
improve ($+7.7$ pass@1, $+2.3$ pass@5). qwen2.5:14b never emitted malformed
JSON to begin with ($0\to0$), so the schema has nothing to fix and changes
nothing---pass@5 is identical, pass@1 moves $+0.5$, well inside the
$\approx\pm3$ standard error, and its failure-mode counts barely shift
(\emph{wrong structure} $28\to26$, the rest within one). For qwen3.5-9b the
same mechanism is catastrophic: pass@1 drops 68.2 points and pass@5 72.8,
while repairing only three malformed calls.

The collapse is deterministic rather than stochastic. pass@5 recovers only to
22.7\%, so resampling five times almost never rescues a failed case, and the
per-category breakdown is degenerate: $0.0/0.0$ on eight of twelve
categories---\code{mapf\_basic}, \code{mapf\_explicit}, \code{mapf\_spread},
\code{parallel}, \code{sequence}, \code{formation\_create},
\code{formation\_move}, \code{formation\_complex}---while scoring $100/100$ on
\code{idle}. \emph{Wrong structure} rises from 11 to 131 and \emph{wrong
robot-id set} from 0 to 32 (cf.\ Table~\ref{tab:e1-failuremodes}).

\emph{The mechanism is a key-order inversion, and it is measurable.} The
common reading of such a collapse---that the plan degenerates to the simplest
branch of the \code{oneOf}---is not what the responses show. Counting the
top-level node type actually emitted, \code{idle} accounts for 104 of 220
calls but \code{sequence} and \code{parallel} together account for 109, so
\code{idle} does not dominate. What happens is narrower: two of the six
branches become unemittable. \code{mapf} goes $58\to0$ at the top level and
\code{formation} $7\to0$; counting every nesting depth, \code{formation} is
never emitted once in 220 constrained calls and \code{mapf} falls $268\to53$,
surviving only nested inside a \code{sequence}. This also rules out recursion
as the cause, since \code{sequence} and \code{parallel} are the only branches
that use the recursive \code{\$ref} and they are untouched.

The cause is visible in key order. Unconstrained, qwen3.5-9b emits
\code{type} first in every object; under the schema it emits every object with
its keys in strict alphabetical order, in 220 of 220 nodes. Because
\code{type} sorts last in all six branches, the model must commit to a branch
by emitting a \emph{content} key before it has named the node type, and branch
selection falls to whichever required key sorts first. That key is
\code{reason} for \code{idle}, \code{steps} for \code{sequence}/\code{parallel}
and \code{formation\_id} for \code{disband}---and the observed first-key
histogram matches the surviving branches exactly (\code{reason} 104,
\code{steps} 109, \code{formation\_id} 4). For the two branches that vanish it
is \code{goals} and \code{follower\_ns}, which the model never selects to open
a plan object.

One step of this is correlational rather than causal, and we mark it as open.
Alphabetical ordering explains why the discriminator arrives last, and hence
why the branch must be committed on a content key; it does not by itself
explain why \code{goals} is chosen \emph{exactly zero} times in 220 calls.
A mere reordering should depress that probability, not annihilate it. The
natural conjecture is that an opening \code{"goals"} token has essentially no
mass in the model's distribution over plan-object prefixes---in ordinary JSON
an array-valued content field does not begin an object---so the constrained
sampler renormalises over the alternatives that do, and the absorbing state is
reached on the first token rather than accumulated over the object. We have
not tested that, and a token-level probe of the constrained sampler would
settle it.

The inversion also corrects what the free text shows. It is the \code{reason}
field inside the degenerate plan that preserves the request---echoing at least
60\% of the prompt's content words in 57\% of idle responses, against 41\% for
\code{reply}---while \code{reply} confabulates a justification for idling
(``send cyan to cafeteria'' $\to$ \code{reason} ``cyan to cafeteria'', reply
``Stopping all robots.''). This follows from the same reordering: unconstrained
the model emits \code{reply} then \code{plan}, and under the schema
\code{plan} then \code{reply}, so it commits to a node type and then
rationalises it. The model is not prevented from expressing an answer it
knows; it records the intent, commits to the wrong branch, and justifies the
result.

\emph{A schema ladder isolates the responsible construct.} To separate the
\code{oneOf} from the recursion it contains, we re-ran qwen3.5-9b under three
derived schemas: \textbf{S2}, the shipped schema minus the \code{sequence} and
\code{parallel} branches (four-branch \code{oneOf}, no \code{\$ref}, no
\code{\$defs}); \textbf{S3}, one schema per node type with \code{type} pinned
by a single \code{const} and no \code{oneOf} at all; and \textbf{S1-no-idle},
the shipped schema minus its cheapest branch. Each variant is derived
programmatically from \code{PLAN\_RESPONSE\_SCHEMA} and asserted at import to
reproduce it exactly when all six branches are kept, so the ladder cannot
drift from the schema it is meant to explain.

Restricted schemas cannot express every reference answer, and scoring them
over all 44 cases would measure \emph{``the grammar forbids the right answer''}
rather than \emph{``the grammar breaks the model''}. Each variant is therefore
scored only on the cases it can express, with the baseline and S1 recomputed
on the same subset; Table~\ref{tab:e2-ladder} reports subset sizes, and none
of its figures are comparable to the full-44 numbers in
Table~\ref{tab:e2-summary}.

Three readings follow, and they agree with the emitted-node evidence above.
\emph{Recursion is not the cause}: S1 and S2 are both exactly $0.0/0.0$ on the
mapf subset, so deleting the recursive branches and every \code{\$ref} changes
nothing. Their difference on the 23-case subset ($34.8/39.1$ vs.\ $37.4/43.5$)
is 2.6 points, inside the standard error, and we read it as noise, not as a recursion
effect in the opposite direction. \emph{The \code{oneOf} is}: pinning
\code{type} to a single \code{const} restores \code{mapf} in 65 of 65 calls,
against 0 of 65 under both S1 and S2. \emph{And the collapse is not simply a
flight to the cheapest branch}: removing \code{idle} does not bring \code{mapf}
back, it relocates the degeneracy to \code{sequence} (43 of 65) and
\code{disband} (15), with \code{mapf} still at exactly zero. What the model
cannot do is \emph{select} the branch; filling it was never the problem.

S3's \emph{pass rate} must not be read as a benefit of constrained decoding,
and we flag this because the comparison is inviting and wrong. S3 pins the node
type by \code{const}, and node type is exactly what the validators check first;
\emph{wrong structure} is qwen3.5-9b's dominant failure mode under the schema
($11\to131$). On the mapf subset S3 therefore tells the model the answer to the
question it is being scored on, and its $84.6/92.3$ is not comparable to the
unconstrained $81.5/84.6$---one condition has half the task solved for it in
advance. What S3 licenses is the structural claim only: the \code{mapf} branch
is reachable, its body is filled correctly when reached, and the failure is
located in branch \emph{selection}. Whether constraining decoding helps a model
that must still choose is not something this ladder measures.

\emph{Scope.} Diagnostics place the trigger in the model and this schema
rather than in the surrounding code---though the runtime turns out to matter
too, which we could not see from one stack and correct in
Sec.~\ref{sec:res-e2c}. No chat template injects the schema into the prompt, nothing on
the outbound path sorts keys, and the request bodies for the two qwen3.5
models differ only in the model name, with the schema reaching the wire in
declaration order. The grammar itself is any-order: qwen3.5:4b reproduces the
\code{required} arrays exactly and qwen2.5:14b emits \code{type} first in
220/220 nodes, so the same grammar accepts both orderings. On a toy schema
with no \code{oneOf}, no recursion and no plan vocabulary---and a worked
example putting \code{type} first---qwen3.5-9b still alphabetises (5/5), and
with three keys it places \code{type} in the middle, which excludes mere
reversal. The behaviour is therefore a schema-mode output convention learned
by qwen3.5-9b, harmless in itself, that is fatal only in contact with a
\code{oneOf} discriminated by a \code{type} field. Sec.~\ref{sec:res-e2c}
qualifies this once more: the convention is the model's, but whether it is
expressed at all depends on the decoding engine.

We resist two tempting generalisations. Model size is not the axis:
qwen2.5:14b is larger than qwen3.5-9b and is unaffected. Nor is qwen3.5:4b
``ignoring'' the schema while the larger model obeys it---4b is demonstrably
constrained, its optional-property use collapsing from 103 emissions to 0 on
otherwise byte-identical prompts, and both models emit schema-valid JSON.
What differs is an orthogonal ordering convention. The generalisable claim is
therefore about schema design rather than about model scale: \emph{a
\code{oneOf} discriminated by a \code{type} field is unsafe under constrained
decoding on any model that alphabetises keys in schema mode}, because the
discriminator is then emitted after the fields that distinguish the branches.
We state that at the branch counts actually tested---six and four, both of
which fail. A two-branch union did not reproduce the effect in an aborted side
probe (a toy \code{move}/\code{wait} union, $N{=}5$: qwen3.5-9b chose correctly
3/5 and opened objects with \code{goals}, qwen3.5:4b 4/5), which is ten calls
and is offered only as a reason to scope the claim rather than as a result.

\emph{Remedies, none of which we have tested.} The ladder localises the fault
but does not supply a fix, and we are explicit that the two candidates below
are untested. S3 is a diagnostic, not a proposal: a schema that can express one
node type is unusable in deployment, because the system does not know before
the operator speaks whether the answer is a movement, a formation, or a
refusal. The first candidate is instead a \emph{fixed envelope}: pin the
top-level node to \code{sequence} and move the union inside its \code{steps}.
The data point toward this rather than away from it---under S1 the model emits
\code{mapf} 53 times nested inside a \code{sequence} while never emitting it at
top level, and under S1-no-idle the degeneracy moves \emph{into}
\code{sequence} (43 of 65)---so the branch decision appears to be tractable
once a container is already open. Unlike S3 this keeps the full grammar and is
deployable, but we have not run it. The second candidate is renaming the
discriminator so that it sorts before every content key (\code{action} rather
than \code{type}, which precedes \code{follower\_ns}, \code{formation\_id},
\code{goals}, \code{reason} and \code{steps}). It follows directly from the
mechanism and is a one-line change; it is also the obvious test to have run,
and we did not run it. Both are stated as predictions the mechanism makes, and
either could fail.

\emph{The deployment hazard is in the defaults, and the obvious fix makes it
worse.} Two parameters interact here. \code{\_stream\_and\_parse()} tests
\code{tool\_calling\_enabled} first and routes to the tool loop when it is
set; the schema is applied only on the other branch, inside
\code{\_stream\_plain()}. The two are therefore mutually exclusive in
practice, and the code says so---it logs a warning when both are enabled,
noting that \code{structured\_output\_enabled} will not constrain those turns.
The declared defaults in \code{chat\_server.py} are
\code{tool\_calling\_enabled} \emph{false} and
\code{structured\_output\_enabled} \emph{true}, while
\code{orchestrator.yaml} ships both \emph{true}. The deployed configuration
thus avoids constrained decoding entirely, and only because tool calling
happens to be switched on: the schema is enabled in the file but never
reaches the model. The code defaults are the combination E2 measures at
19.1\%, and an operator following the warning's own advice---disable tool
calling, since it suppresses structured output anyway---moves the system from
the unconstrained path onto exactly that combination. The hazard is
conditional on model choice rather than universal, since
\code{orchestrator.yaml} names \code{mistral-small3.1} rather than one of the
models measured here; but a defaults pair that is safe only by accident, and
that a documented remedy turns unsafe, is a configuration defect independent
of which model is loaded.

\emph{Symbolic grounding is load-bearing for the small model and inert for the
large one.} qwen3.5:4b degrades monotonically on pass@5 as scaffolding is
removed, losing 9.1 points by \emph{coords-only},
with \emph{wrong structure} rising 17\,$\to$\,24 and \emph{wrong robot-id
set} 0\,$\to$\,3: stripped of aliases and zones it starts mis-resolving which
robots and which structure the request implies. qwen3.5-9b loses nothing
(95.5\% pass@5 in all three grounding conditions) and moves $+3.2$ and $+1.8$
on pass@1---both inside the $\approx\pm3$ standard error, so the honest
reading is that removing the scaffolding costs the larger model nothing rather
than that it helps. An earlier version of this paper read the same cells as a
$+9.1$ gain in both reduced conditions and concluded that the heuristics
paragraph is actively counterproductive; that conclusion was an artefact of
the first-sample estimator and does not survive using all the data. What
remains is still an answer to RQ2's question of what the
$\approx$9{,}700-token prompt buys, just a weaker one: for the larger model
the most expensive symbolic block buys nothing measurable, and for the small
model the \emph{aliases and zones} carry whatever value there is.

The \emph{unp.} column carries a second, independent effect that the pass rates
hide. Trimming the map block monotonically reduces malformed JSON in both
models: $16\to11\to11$ for qwen3.5:4b and $6\to1\to0$ for qwen3.5-9b, which for
the larger model is the malformed-output failure mode disappearing entirely
without any schema. This runs in the same direction as the heuristics result
and is worth separating from it: a shorter prompt appears to buy \emph{cleaner
output} independently of whether it buys better plans. For qwen3.5:4b the two
effects point opposite ways---it emits better-formed JSON on the reduced
prompts and nonetheless plans worse---so output well-formedness and planning
accuracy are not the same axis and a prompt-budget decision cannot be made on
either alone. At five and six failures respectively these counts are small,
and we report the direction rather than an effect size.

\emph{Reading with appropriate caution.} The grounding effects are at or below
the resolution of this design. With 220 calls per cell the standard error on a
pass@1 near 80\% is about 3 points before any correction for the fact that
five repeats of one case are not independent draws, so the only grounding
figure in the table that clears it comfortably is qwen3.5:4b's
\emph{coords-only} pass@5 drop ($-9.1$). We report the others as directions,
not effect sizes, and specifically decline to build on the $+3.2$/$+1.8$ moves
for qwen3.5-9b. The schema result on the same model needs no such hedging: a
68.2-point drop with eight of twelve categories at exactly zero is not a
sampling artifact at any plausible interval.

\emph{What E2 does not measure.} Sec.~\ref{sec:e2} proposed five factors; two
are reported here. Tool calling is deferred to E3.
The offline harness cannot exercise it faithfully: \code{check\_occupancy}
subscribes to a live \code{LaserScan} and so requires the simulator;
\code{verify\_plan\_execution\_state} verifies a post-execution state that
does not exist offline; the task tools are irrelevant to all 44 cases; and
\code{get\_robot\_position}/\code{get\_positions} return data the harness
already injects into the prompt. Only two pure geometry helpers would carry
signal, so an offline tool arm would weigh the full cost of the tool path
against a fraction of its benefit. Standing up a fake-odometry publisher to
feed the tools was considered and rejected: that plumbing would only
transport poses the harness already holds, leaving the measurement
unchanged. This reverses the intention stated in Sec.~\ref{sec:e2}; the
objection recorded there---that measuring the factor in E3 confounds planning
mode with execution noise---remains valid and is the price of the change.
Live pose context, goal auto-spread, and context budget are likewise not
measured: the first is uninterpretable as a single rate because several cases
exist \emph{because of} their context, and the latter two are not on the
harness code path at all (\code{goal\_spread\_enabled} is applied by
\code{\_postprocess\_plan()} after the model returns, so E1 neither used nor
could have used it).

One side effect of the schema factor is worth recording, since it bears on
auto-spread from the other direction. \code{spread} is the only optional
property in the plan schema, and constrained decoding suppresses it sharply:
$103\to0$ emissions for qwen3.5:4b, $99\to0$ for qwen3.5-9b, $191\to9$ for
qwen2.5:14b. Optional properties are not forbidden by the grammar---14b still
emits nine---but they become rare enough to treat as unavailable. The
capability survives only because \code{\_validate\_node()} infers spreading
from goal arity when one centre is given for several robots; 4b's
\code{mapf\_spread} score in fact rises under the schema. That inference is
load-bearing in a way its own comment does not suggest, and removing it would
silently disable the feature for any deployment using structured outputs.

The within-cell evidence is stronger than the between-model evidence, because
it removes every difference except the one under test. Hosted qwen3.5-9b
alphabetises on only part of its calls, which splits the same cell---same
model, same schema, same prompts---into two populations:

\begin{center}\footnotesize
\begin{tabular}{lccc}
\toprule
Key order & calls & pass rate & \code{mapf} at top level \\
\midrule
\code{type} first  &  93 & \textbf{91.4\%} & 35 \\
mixed within a plan &   2 & 0.0\% & 0 \\
alphabetical        & 117 & \textbf{23.9\%} & \textbf{0} \\
\midrule
no parseable plan   &   8 & 0.0\% & --- \\
\bottomrule
\end{tabular}
\end{center}

The last row is not a rounding remainder: 8 of the 220 calls produced JSON
that does not parse, so no key order can be read off them. They are failures
and are counted as such in Table~\ref{tab:e2c-hosted}; excluding them from the
split would flatter both buckets, so they are shown rather than dropped.

The \code{mapf} branch is emitted 35 times when the discriminator comes first
and \emph{exactly zero} times when it does not, reproducing the local
$58\to0$ result inside a single condition. This is the prediction of
Sec.~\ref{sec:res-e2} stated as a dose relationship rather than a comparison:
where the ordering convention appears, the branch disappears with it.

\emph{But the trigger is not the model alone, and Sec.~\ref{sec:res-e2}
overstated that.} We wrote there that diagnostics place the trigger in the
model rather than in the stack. The hosted data contradicts the second half.
The same weights alphabetise 220/220 nodes under Ollama and 60.6\% under
OpenRouter, and the split is not random: it tracks which provider served the
call. Seventeen cases re-run on a single pinned provider (SiliconFlow)
alphabetised on 100\% of calls, while the cases served by the router's own
choice did so on 28.6\%, a minority in every case family. The decisive pair is
\code{parallel\_01} against \code{parallel\_02..04}---identical plan shape,
different provider---where the first alphabetises 0/5 and passes 5/5, and the
others alphabetise 5/5 and pass 0/5.

The corrected statement is an interaction, not a property: qwen3.5-9b carries
a latent schema-mode ordering convention that no other model tested shares,
and whether that convention is expressed is decided by the constrained-
decoding engine. Ollama expresses it always, SiliconFlow always, the remaining
providers mostly not. This makes the deployment hazard \emph{worse} rather
than better, because it is invisible in exactly the way that matters: the same
model name and the same schema produce 91\% or 24\% depending on infrastructure
the caller does not choose and cannot see.

It also means the 51.4\% in Table~\ref{tab:e2c-hosted} is an average over two
decoders in proportions we did not control, and must not be read as
``qwen3.5-9b scores 51.4\% under schema when hosted''. We report it for
completeness and rest no argument on it; the argument rests on the within-cell
split, which does not depend on the mixture. A clean per-engine measurement
needs the same cases run against each provider deliberately, which is one
experiment we have specified and not yet run.

\emph{Model size is still not the axis.} Sec.~\ref{sec:res-e2} declined to make
it one, on the grounds that qwen2.5:14b is larger than qwen3.5-9b and
unaffected. The hosted set strengthens that: the three unaffected models span
9B to 550B parameters and four vendors, so susceptibility is not a threshold
being crossed---it is one model's convention.

What the hosted set does \emph{not} show, and an earlier draft of this section
claimed, is that the schema \emph{helps} a large model. qwen3.5-397b-a17b
moves $+1.8$ points under it, not the $+9.1$ we first reported, and its
schema-on rate is 95.0\%, not a clean 44/44. Both of those were products of
scoring pass@1 on the first repeat: the model fails three of its 44 cases on a
majority of attempts, and on all three the first attempt happened to succeed.
Counting all 220 attempts, the correct statement is the weaker one---for a
model that does not alphabetise, constrained decoding is free rather than
beneficial. That is still the claim the guard layer needs, since the schema is
there to remove malformed output and not to improve planning; it is simply not
the stronger claim.

\section{Conclusion}

\pending{Full claim pending E3. The intended claim remains: a small typed
plan grammar plus deterministic guards lets a modestly-sized locally-hosted
model supervise a 20-robot fleet, and the gap between plan-level accuracy and
mission-level success is where the engineering value sits---E3 is the
experiment that can actually support that sentence.}

What E1 and E2 support is narrower but not nothing. First, bare planning
accuracy without any of the system's guards or repair loops sits at
70--87\% pass@1 across five locally-hosted 3.4--24B models under a realistic
$\approx$9{,}700-token prompt---a fleet-supervision system built on a single
unguarded plan call would fail between one command in three and one in eight
\emph{regardless of which model is deployed}, which is the quantitative case
for the defence-in-depth design of Sec.~\ref{sec:guards} rather than an
assumption behind it. Second, the five models' failures are not
interchangeable, and not even uniformly noisy: the smallest model's errors
look like sampling noise (pass@5 recovers most of the gap to a near-perfect
pass@1), while two mid/large models repeat the \emph{identical} validator
complaint---a malformed \code{offsets\_x}/\code{offsets\_y} array in
formation nodes---on retry after retry. That argues for model-specific
schema-repair logic rather than a single fixed remediation budget applied
uniformly. Third, escalation splits into a judgment and a protocol, and only
the protocol is weak. Recognition of ambiguity is uniform and good: every
model tested---five local, and four hosted spanning 9B to 550B parameters and
four vendors---declines to act on the underspecified \emph{form a triangle}
and asks the right question, in most cases with byte-identical wording. What
they disagree on is how to \emph{signal} it, and an earlier version of this
paper read that disagreement as a capability gap because the validator scored
the prefix rather than the behaviour (Sec.~\ref{sec:e1-results}). The
component worth placing outside the model is therefore the protocol---a
deterministic check routing any idle plan that carries a question to the
operator, whichever prefix the model chose---rather than the judgment. One
genuine judgment failure does survive the correction, a model answering
\emph{repeat the last command} with a \code{mapf}, and it is the shape of
error that matters most: well-formed, confident, and wrong. It is also a
single case on a single model, and we do not build on it. Fourth, the
categories that are hardest across the board---formation staging order,
escalation judgment---are exactly the categories the plan grammar
(Sec.~\ref{sec:planlang}) and the guard layer were built to catch
downstream, which is a consistency check on the architecture rather than a
result about it.

E2 adds a fifth point that we did not anticipate and that cuts against one of
our own design choices. Schema-constrained decoding---listed above as the
first line of defence---is not a free safety net. It repairs the failure mode
it was built for only where that failure mode exists, does nothing where it
does not, and on one model destroys planning outright, by a mechanism
(alphabetised keys meeting a \code{type}-discriminated \code{oneOf}) that has
nothing to do with planning ability. We can locate the fault
precisely---the schema ladder puts it in branch \emph{selection}, not in
recursion and not in filling a branch once chosen---but we stop short of
claiming a fix: the two remedies the mechanism suggests, a fixed
\code{sequence} envelope and renaming the discriminator so it sorts first, are
both untested.

Six distinct sets of weights have now been run under the schema across two
inference stacks---three locally and four hosted, with qwen3.5-9b in both---and
they sharpen the finding in two directions at once
(Sec.~\ref{sec:res-e2c}). It is narrower than we feared: five of the six emit
the discriminator first and none of those five is measurably harmed, so for a
model that does not alphabetise the constraint is free. And it is more
insidious than we thought: the offending convention belongs to the model, but
whether it is expressed belongs to the decoding engine. The same weights
alphabetise on every node under one runtime and on a minority under another,
and pass 24\% or 91\% of calls accordingly---a swing driven by infrastructure
the caller does not choose and cannot see from the model name.

The wider lesson for defence-in-depth is therefore stronger than
per-model measurement. A guard is only deterministic from the system's side;
from the model's side it is another distribution shift, and that shift is a
property of the model \emph{and} the stack serving it. Whether the remaining
guards actually close the plan-to-mission gap in a running fleet, and whether
this holds under tool calling instead of constrained decoding, is what E3 is
for.
