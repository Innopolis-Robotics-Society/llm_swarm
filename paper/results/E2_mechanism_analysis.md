# E2 follow-up — mechanism of the qwen3.5-9b schema collapse

Post-hoc analysis over the E2 raw runs plus three new experiments. Everything
here concerns *why* schema-constrained decoding reverses sign between
`qwen3.5:4b` and `qwen3.5-9b`, and how far that result generalises.

Generated by:

- `paper/results/analyze_e2_nodes.py` → `e2_node_distribution.json` (Part 0)
- `paper/results/raw/e2_ladder_driver.sh` → `e2_ladder_*.json` (Part 2)
- `paper/results/build_e2_ladder.py` → `e2_ladder_summary.json` (Part 2)

## Part 0 — what the model actually emits (no new model calls)

### The headline correction

Sec. 6.2 states that under the schema qwen3.5-9b "emits an `idle` plan nearly
regardless of the request." That is not what the data show, and the true
picture is sharper.

Top-level plan node type, qwen3.5-9b, 220 calls per cell:

| node type | schema off | schema on |
|---|---:|---:|
| `mapf` | 58 | **0** |
| `formation` | 7 | **0** |
| `sequence` | 73 | 85 |
| `parallel` | 26 | 24 |
| `idle` | 41 | 104 |
| `disband` | 5 | 4 |
| unparseable | 10 | 3 |

`idle` does not dominate — `sequence` is still emitted 85 times, and
`sequence` + `parallel` together (109) outnumber it. What actually happens is
narrower and more specific: **two of the six `oneOf` branches become
unemittable.** `mapf` goes 58 → 0 and `formation` 7 → 0 at the top level.

Counting nodes at *every* nesting depth makes it starker still:

| node type | schema off (all depths) | schema on (all depths) |
|---|---:|---:|
| `mapf` | 268 | 53 |
| `formation` | 69 | **0** |
| `idle` | 46 | 220 |
| `disband` | 14 | 71 |

`formation` is never emitted anywhere in 220 constrained calls. `mapf` survives
only nested inside a `sequence`/`parallel` (53 occurrences) and never as the
top-level plan.

### Which hypothesis this supports

The `oneOf` branch order in `plan_schema.py:_NODE_SCHEMA` is
**mapf, formation, disband, idle, sequence, parallel**.

- **Branch-order bias — refuted.** `mapf` is the *first* alternative and it is
  exactly the one that drops to zero.
- **Cheapest-valid-exit — partially supported.** The two branches that vanish
  are the two most expensive: `formation` (7 required fields, three parallel
  arrays) and `mapf` (4 required fields, including `goals`, a nested
  array-of-arrays). The two that surge are the cheapest leaves, `idle` (2
  required fields, 46 → 220) and `disband` (3 required, 14 → 71). But the
  simple form of the hypothesis — "collapse concentrates on `idle`, near-zero
  of the rest" — is wrong: `sequence` and `parallel` are unaffected.
- **Recursion — refuted as the cause.** `sequence` and `parallel` are the only
  two branches that use the recursive `$ref`, and they are emitted freely and
  nest correctly. Whatever breaks, it is not the recursion.
- **Model-specific — supported.** `qwen3.5:4b` under the *identical* schema
  shows no such skew (top-level `mapf` 50 → 52, `formation` 4 → 4 against its
  own baseline). The grammar therefore permits the correct answers; this model
  cannot reach them.

### The key-order inversion

The mechanism shows up in emitted key order, and it is unambiguous. Counting
key sequences over every emitted object:

| cell | top-level order | node key order |
|---|---|---|
| 9b, schema **off** | `reply, plan` (214) | `type, robot_ids, goals, spread, reason` (182) |
| 9b, schema **on** | `plan, reply` (217) | `reason, type` (220); `steps, type` (110); `formation_id, reason, type` (71); `goals, reason, robot_ids, type` (53) |
| 4b, schema **on** | `reply, plan` (218) | `type, robot_ids, goals, reason` (291) |

Under the schema, qwen3.5-9b emits **every object with its keys in strict
alphabetical order**, in 220/220 nodes. Unconstrained, it always emits `type`
first. `qwen3.5:4b` under the same schema keeps `type` first, so the grammar
does not *force* alphabetical order — this model *adopts* it.

That inversion is the mechanism. Alphabetical order puts `type` **last** in
every node, so the model must commit to a branch by emitting a *content* key
before it has named the node type. The alphabetically-first required key of
each branch is:

| branch | first key under alphabetical order | emitted at top level? |
|---|---|---|
| `idle` | `reason` | yes — 104 |
| `sequence`/`parallel` | `steps` | yes — 109 |
| `disband` | `formation_id` | yes — 4 |
| `mapf` | `goals` | **no — 0** |
| `formation` | `follower_ns` | **no — 0** |

The four branches whose alphabetically-first key is a plausible opening token
survive; the two whose first key is `goals` or `follower_ns` — tokens that
never begin a plan object in the model's training distribution — are
unreachable. The observed first-key histogram matches the surviving branches
exactly: `reason` 104 = `idle` 104, `steps` 109 = `sequence` 85 + `parallel`
24, `formation_id` 4 = `disband` 4.

### A second correction: it is `reason`, not `reply`, that stays correct

Sec. 6.2 states that "the free-text `reply` field still states the correct
intent." It is the other way round. Over the 104 idle-plan responses:

- `reason` echoes ≥60% of the prompt's content words in **57%** of responses
- `reply` does so in only **41%**

and the replies actively confabulate justifications for idling:

| prompt | emitted `reason` | emitted `reply` |
|---|---|---|
| send cyan to cafeteria | `"cyan to cafeteria"` | "Cyan robots are already at upper_engine in formation; please disband first…" |
| orange robots go home | `"orange robots go home"` | "Stopping all robots." |
| drive yellow to navigation | `"yellow to navigation"` | "Yellow robots are already near their home position at navigation; no movement needed." |

This follows directly from the key-order inversion. Unconstrained the model
emits `reply` **then** `plan`; under the schema it emits `plan` **then**
`reply`. Having been forced into `type: idle`, it then writes a reply
consistent with the plan it has already committed to. The model does not
"know the answer while the grammar prevents it from expressing it" — it
records the correct intent in `reason`, commits to the wrong node type, and
then rationalises.

### Incidental finding: optional properties are heavily suppressed

`spread` is the one *optional* property of the `mapf` branch. Nodes carrying a
real `spread` key, constrained vs unconstrained:

| model | schema off | schema on |
|---|---:|---:|
| qwen3.5:4b | 103 | 0 |
| qwen3.5-9b | 99 | 0 |
| qwen2.5:14b | 191 | 9 |

Optional properties are not *forbidden* by the grammar — 14b still emits nine
of them — but their use collapses. For the two qwen3.5 variants it reaches
exactly zero across ~500 emitted nodes each. Since the prompts are
byte-identical between a model's baseline and its schema-on run, this step
change is also independent confirmation that the schema genuinely reached the
backend in all three runs.

The capability is not lost, because `plan_executor._validate_node` infers
`spread` from goal arity when one centre is given for several robots
(`plan_executor.py:135-136`). 4b's `mapf_spread` score in fact *rises* under
the schema (50.0/100.0 → 100.0/100.0). This is a latent robustness in the
executor absorbing a real limitation of constrained decoding, and it is worth
recording because it is the kind of thing that silently stops working if that
inference is ever removed.

## Part 1 — a third model, different family

`qwen2.5:14b`, schema on, grounding full, E1b protocol (44 cases, N=5,
temperature 0.1, 2048-token budget, 32,768-token context, 220 calls, 0
timeouts). Its schema-off baseline is the existing `e1b_qwen2.5-14b.json`;
reuse was gated on the same prompt fingerprint
(`42d660fe…8c37ed`), which matched.

| | pass@1 | pass@5 |
|---|---:|---:|
| baseline (E1b) | 72.7% | 79.5% |
| schema on | 70.5% | 79.5% |
| Δ | −2.2 | ±0.0 |

**The schema does essentially nothing to qwen2.5:14b.** Its node distribution is
unchanged (`mapf` 57 → 61, `formation` 9 → 7, `sequence` 89 → 91, `idle` 30 →
30), it emits `type` first in 220/220 nodes, and its failure-mode counts barely
move (`wrong_structure` 28 → 26, `wrong_goals` 10 → 11, the rest identical).

Its `unparseable_json` count is **0 in both cells** — 14b never emitted
malformed JSON in the first place, so the schema had nothing to fix. That
completes a tidy three-way picture of what constrained decoding actually buys:

| model | `unparseable_json` off → on | net effect |
|---|---|---|
| qwen3.5:4b | 16 → 1 | the feature working as designed (+4.5 pass@1) |
| qwen2.5:14b | 0 → 0 | nothing to fix, nothing gained (−2.2) |
| qwen3.5-9b | 6 → 3 | fixes 3 calls, destroys 145 (−65.9) |

*(Note on bookkeeping: the `<unparseable>` bucket in `e2_node_distribution.json`
is not this number. `_parse_response` both parses and validates, so that bucket
also catches cross-field failures like `robot_ids(4) != goals(22)`. The counts
in this table come from the E1b failure-mode taxonomy, which is the one
comparable to Table 5.)*

This is the third of the brief's three possible outcomes' middle case: the
collapse is isolated to qwen3.5-9b specifically. It also kills the most
tempting reading of the two-model result. **Model size is not the axis**: 14b is
larger than 9b and is unaffected, so "small model robust, large model fragile"
is refuted rather than confirmed by the third data point.

Across all three models the correlation is exact:

| model | key order under schema | outcome |
|---|---|---|
| qwen3.5:4b | declaration (`type` first, 219/220) | +4.5 pass@1 |
| qwen2.5:14b | declaration (`type` first, 220/220) | −2.2 pass@1 |
| qwen3.5-9b | **alphabetical (220/220)** | **−65.9 pass@1** |

Every model that keeps `type` first is unharmed; the only model that
alphabetises is the only model that collapses.

## Part 2 — schema ladder (qwen3.5-9b)

Three schemas derived programmatically from `PLAN_RESPONSE_SCHEMA`, with an
import-time assertion that rebuilding with all six branches reproduces it
exactly:

- **S2** — minus `sequence`/`parallel`: four-branch `oneOf`, no `$ref`/`$defs`
- **S3** — one branch per schema, `type` pinned by `const`, no `oneOf`
- **S1-no-idle** — minus the `idle` branch, still recursive

**Scoring**: each variant is scored only on the cases it can express, with the
baseline and S1 recomputed on that same subset. These figures are **not**
comparable to the full-44 numbers in Table 6.

| variant | plan node | 23-case subset | 13-case mapf subset |
|---|---|---|---|
| schema off | — | 73.9/82.6 | 76.9/84.6 |
| S1 | 6-branch, recursive | 21.7/30.4 | **0.0/0.0** |
| S2 | 4-branch, no recursion | 26.1/34.8 | **0.0/0.0** |
| S3 | 1 branch, no `oneOf` | **78.3/87.0** | **84.6/92.3** |
| S1-no-idle | 5-branch, recursive | — | **0.0/0.0** |

### Verdict

**Recursion — refuted.** S1 and S2 are both exactly 0.0/0.0 on the mapf
subset. Deleting the recursive branches and every `$ref`/`$defs` changes
nothing.

**`oneOf` — confirmed as the cause.** S3 restores `mapf` in 65/65 calls, against
0/65 under both S1 and S2. The `mapf` shape was never the problem — selecting
it was.

> **Correction.** An earlier version of this file and of §6.2 compared S3's
> 84.6/92.3 against the unconstrained 76.9/84.6 and concluded that constrained
> decoding is "a net gain once the model no longer has to choose a branch."
> **That comparison is invalid and has been withdrawn.** S3 pins the node type
> with a `const`, and node type is exactly what the validators check first —
> `wrong_structure` is this model's dominant failure mode under the schema
> (11 → 131). On the mapf subset S3 hands the model the answer to the question
> it is scored on. S3 licenses the *structural* claim only: the branch is
> reachable and fills correctly once reached. It is a **diagnostic, not a
> deployment proposal** — a schema expressing one node type is unusable when
> the system cannot know in advance whether the operator wants a movement, a
> formation, or a refusal.

*(S1 vs S2 on the 23-case subset, 21.7/30.4 vs 26.1/34.8, is one to two cases at
N=5 — noise, not a reverse recursion effect.)*

**Cheapest-valid-exit — refuted in its strong form.** Removing `idle` does not
restore `mapf`. The degeneracy simply relocates to `sequence` (43 of 65) and
`disband` (15), with `mapf` still at exactly zero. A pure cheapest-exit
account predicts pressure back toward `mapf` once the cheap branches are
removed; that does not happen. What survives is the weaker statement that
among *selectable* branches the model prefers the cheap ones.

Emitted top-level types on the mapf subset, for the record:

| variant | emitted |
|---|---|
| schema off | `mapf` 58 |
| S1 | `idle` 55, `sequence` 8, `parallel` 1 |
| S2 | `idle` 64, `disband` 1 |
| S3_mapf | `mapf` 65 |
| S1-no-idle | `sequence` 43, `disband` 15, `parallel` 6 |

*(`s3_idle` scored 31/45 and `s3_disband` 5/5. The `s3_idle` shortfall is
content, not structure — the `escalate_*` cases require a specific `reason`
prefix — so it should not be read as a schema effect.)*

## Side task — why does qwen3.5-9b alphabetise and the others do not?

### Part A: it is not the prompt, the client, or the payload

| checked | result |
|---|---|
| schema injected into prompt by the chat template? | **no** — the 9b template references JSON only in its tool-calling block; it never renders the response schema |
| anything sorting keys on the outbound path? | **no** — the only `sort_keys=True` in the package are the prompt fingerprint (`benchmark_ch3.py`) and three `mission_supervision.py` helpers, neither on this path |
| do the two outbound bodies differ? | **only in `model`** — `format` present in both, schema on the wire in declaration order (`type, robot_ids, goals, spread, …`) |
| did the schema really apply to the 4b run? | **yes** — see below |
| Ollama version | 0.30.11 |

The 4b check is load-bearing: had that cell silently run unconstrained, the
"reverses sign between two models" headline would instead be a
mis-instrumented run. It holds. With byte-identical prompts, the only
difference between 4b's baseline and its schema-on run is the `format` field,
and across that change `spread` usage goes 103 → 0 while unparseable JSON goes
16 → 1. An optional field falling to exactly zero over 220 calls is not
sampling drift.

**The grammar is any-order.** qwen3.5:4b's emitted key orders match the
`required` arrays exactly for all five node shapes it produces; qwen3.5-9b
emits the same property *sets* alphabetically; qwen2.5:14b matches declaration
order in 220/220. Same grammar, three models, two different orders, all
accepted — so ordering is permitted, not imposed. (Optional properties are
heavily suppressed but not forbidden: 14b still emits nine `spread` keys.)

### Part B: it is a learned schema-mode convention

A toy schema carrying none of PLAN_RESPONSE_SCHEMA's structure — no `oneOf`,
no recursion, no plan vocabulary, two or three keys — with a system prompt
whose worked example puts `type` first:

| probe | declared order | qwen3.5:4b | qwen3.5-9b |
|---|---|---|---|
| B1 | `type, alpha_first` | `type, alpha_first` (5/5) | `alpha_first, type` (5/5) |
| B2 | `type, alpha_first, zulu_last` | `type, alpha_first, zulu_last` | `alpha_first, type, zulu_last` |

B2 is the decisive one: alphabetical order puts `type` in the **middle**, so
the 9b output cannot be explained as reversal. qwen3.5-9b alphabetises
whenever a response schema is present, on any schema, overriding the
in-context example.

So the answer to "why" is: **qwen3.5-9b has learned to emit alphabetically
ordered keys in schema mode.** Nothing in our stack teaches it that, and the
convention is harmless in itself — B1 and B2 are perfectly valid responses.
It becomes catastrophic only in contact with a `oneOf` discriminated by a
`type` field.

### What this entitles Sec. 6.2 to say

The mechanism is now specific enough to state as a rule rather than as a
model quirk:

> A `oneOf`-discriminated union is unsafe under constrained decoding on any
> model that alphabetises keys in schema mode, because the discriminator is
> then emitted *after* the fields that distinguish the branches, and branch
> selection falls to whichever key happens to sort first.

In `PLAN_RESPONSE_SCHEMA`, `type` sorts last in **all six** branches, so
selection falls to the alphabetically-first required key of each:

| branch | alphabetically-first key | emitted by 9b? |
|---|---|---|
| `idle` | `reason` | yes — 104 |
| `sequence`/`parallel` | `steps` | yes — 109 |
| `disband` | `formation_id` | yes — 4 |
| `mapf` | `goals` | **never** |
| `formation` | `follower_ns` | **never** |

### Aborted follow-on: is the discriminator's sort position the cause?

`e2_discriminator_probe.py` was to test the remedy the mechanism implies — two
identical two-branch unions differing only in the discriminator's *name* (C1
`type`, sorts last; C2 `action`, sorts first) — predicting C1 picks the wrong
branch and C2 the right one. **Stopped after 2 of 4 cells** (~2.7 min/call: the
toy prompt gives a thinking model little to anchor on, so it spends the full
2048-token budget), since the ladder had already established the mechanism.

| cell | correct | key order |
|---|---|---|
| C1 `type`, qwen3.5-9b | 3/5 | `goals, reason, type` (alphabetical) |
| C1 `type`, qwen3.5:4b | 4/5 | `type, goals, reason` (declaration) |

Two things follow. The **key-order split reproduces on yet another schema**,
strengthening Part B. But the **branch loss does not reproduce at two
branches** — 9b opened objects with `goals` and mostly chose correctly. The
failure therefore needs enough competing branches, not merely a discriminated
union; the paper states the rule at the counts actually tested (six and four)
and flags the two-branch observation as preliminary.

C2 never ran, so **the discriminator-rename remedy is untested** and the paper
declines to claim it.

## Remedies the mechanism predicts — both untested

S3 is not one of them (see the correction above). The two deployable
candidates, neither of which we ran:

1. **Fixed `sequence` envelope.** Pin the top-level node to `sequence`; move the
   union inside `steps`. The data point toward it: under S1 the model emits
   `mapf` 53 times *nested inside a sequence* and 0 times at top level, and
   under S1-no-idle the degeneracy moves **into** `sequence` (43/65). Branch
   selection appears tractable once a container is already open. Unlike S3 this
   keeps the full grammar and is deployable.
2. **Rename the discriminator** so it sorts before every content key: `action`
   rather than `type` (`action` < `follower_ns`, `formation_id`, `goals`,
   `reason`, `steps`). One line, and the obvious test to have run.

Both are implemented and ready — `benchmark_ch3.py --schema-variant s4_envelope`
and `--schema-variant s5_action`, with the scoring normalisations documented in
`normalise_plan()` (single-step-sequence unwrapping; `action`→`type` rename).
No results exist and the paper claims none.

### On the tempting inversion — the evidence does not support it

It is tempting to say qwen3.5:4b is not *surviving* the schema but *ignoring*
it, and that the model which breaks is the one following the schema most
faithfully. **That reading should not be written.** 4b is demonstrably
constrained (`spread` 103 → 0, unparseable 16 → 1) and its output conforms to
the grammar; it simply orders keys by declaration, which the any-order grammar
permits. Neither model is more or less compliant than the other — both emit
schema-valid JSON. What differs is an orthogonal stylistic convention that
happens to interact badly with a discriminated union.

Model size is likewise not the axis: qwen2.5:14b is larger than qwen3.5-9b and
is unaffected.
